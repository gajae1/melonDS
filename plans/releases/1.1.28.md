# 1.1.28 — 캡처 중간 접근·AES 태그·DSi 재설정

기준 1.1.27, 검증일 2026-09-10. GR-05, AD-14, AD-17/22의 독립 블록을 기존 코드와 시험 도구로 진행했다. 책임 버전 1.1.28의 성능 과제와 공개 전체 계획은 유지한다.

## 5페이즈

1. **재현:** 실제 ARM9의 캡처 중간 읽기·쓰기/DMA, 공개 AES 벡터, DSi MMIO·I2C 전송·재설정 상태를 정상 경로와 대조했다.
2. **수정:** GPU는 부모가, AES와 DSi reset/I2C는 서로 다른 작업 공간의 작성자가 맡았다. 공유 dispatcher·CMake·저장 형식은 부모가 통합했다.
3. **통합:** 캡처의 완료된 줄을 RAM에 보존하고, AES 태그 입력·인증·IRQ 및 I2C 방향·STOP·완료 상태를 연결했다. 이전 I2C 저장 상태의 누락 정보를 추측하지 않는다.
4. **검증:** 각 블록의 수정 전 반례·수정 후 정상/오류/복원 결과와 최종 Windows 빌드·전체 회귀·통합 Qt 결과를 확인했다.
5. **배포:** 확인된 증분을 버전별 Windows/source 패키지와 포크 master에 반영한다. 실기·실제 게임·다른 플랫폼·장기 수락은 별도로 남긴다.

## 변경과 근거

**캡처:** GL은 진행 중인 캡처를 CPU가 읽어도 모아 둔 렌더 작업을 처리하지 않고 전체 texture를 읽었다. 이후 RAM 동기화가 끝났다고 표시해서 남은 줄도 갱신하지 않았다. 첫 중간 접근에서 이미 샘플링한 줄만 처리하며, 그 프레임의 이후 줄은 캡처할 때 RAM에 반영한다. 아직 캡처하지 않은 RAM과 이미 지난 줄의 CPU 쓰기를 보존한다. 목적지·크기가 바뀌면 이전 구간과 새 목적지의 기존 내용을 보존하고 metadata를 무효화한다. 별도의 레지스터 latch 규칙을 만들지 않고 기존 software의 scanline 적용 경계와 대조했다. 일반 프레임의 일괄 렌더링은 유지한다. [GBATEK 캡처 형식](https://mgba-emu.github.io/gbatek/#dsvideocaptureandmainmemorydisplaymode)

**AES:** CCM 복호화의 FIFO 태그 모드를 구현해 payload 뒤의 16바이트 태그를 소비하고 인증 후 기존 완료 IRQ/DMA 경로로 진행한다. 부분 입력은 기존 FIFO·busy 상태로 보존하며 새 저장 필드는 필요 없다. 짧은 태그의 길이·0 padding은 FIFO/레지스터 검증과 암호화 출력에서 같은 계약으로 처리한다. 독립 암호 결과는 공개 Wycheproof와 NIST 벡터에서 가져왔다. [DSi AES I/O](https://problemkaputt.de/gbatek.htm#dsiaesioports), [고정 Wycheproof 벡터](https://github.com/C2SP/wycheproof/blob/e0df04e0c033f2d25c5051dd06230336c7822358/testvectors_v1/aes_ccm_test.json), [NIST CTR 벡터](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-38a.pdf)

**DSi reset/I2C:** 재설정의 SCFG 값을 기존 setter와 연결해 실제 클럭·카드 MMIO 경로가 레지스터와 일치하게 한다. I2C는 주소의 방향을 보존하고 반대 방향의 데이터 접근을 거부하며 STOP에서 slave를 해제하고 완료 상태 뒤에 IRQ2를 알린다. 기존 BPTWL의 별도 STOP 관례와 카메라의 정상 전송을 유지한다. 재설정 기본값이나 물리 전송 지연을 새로 추정하지 않았다. [I2C 포트](https://problemkaputt.de/gbatek-dsi-i2c-i-o-ports.htm), [Calico 실제 호출 순서](https://github.com/devkitPro/calico/blob/81b75e314d57ed1784545e28554e567f26f572f1/source/nds/arm7/i2c.twl.c), [SCFG 정의](https://github.com/devkitPro/calico/blob/81b75e314d57ed1784545e28554e567f26f572f1/include/calico/nds/scfg.h)

## 검증 결과

Windows x64 Release 빌드 성공. 최종 소스의 전체 CTest는 **517/517 통과, 실패 0, 건너뜀 0**, 병렬도 2에서 66.43초였다. 최종 애플리케이션 객체를 연결한 Qt 검증도 exit 0으로 완료했다. 생성 guest 실행 중 shader·표시·배율 한도 실패, 설정 Cancel·재시도·새 context capability와 guest 상태 보존·정상 종료를 확인했다. SDL dummy audio와 오류 주입 진입점을 사용했으며, 물리 드라이버 고장이나 실제 DSi 게임 부팅을 검증한 결과는 아니다.

- 캡처는 생성 ARM9 프로그램의 VCOUNT polling·LDRH/STRH·실제 DMA와 정상 frame scheduler를 사용한다. 같은 최종 fixture에서 기준 GL 소스는 두 hardware backend가 실패하고 software는 통과했다. 수정 후 3D·2D backdrop·VRAM source B·혼합, 128/256 폭·offset wrap·1x/2x, 과거/미래 줄, 원본·목적지·크기 변경과 중복 접근을 확인했다. 전체 2D 특성·subscanline timing의 실기 oracle은 아니다.
- AES는 실제 DSi MMIO·NDMA와 전체 core 상태를 사용한다. 올바른/잘못된 태그·길이·padding·입력 분할·FIFO 포화·DMA 경계·저장/복원을 확인했다. 호스트가 장치 MMIO를 구동하며 firmware나 guest CPU를 부팅한 결과는 아니다.
- Reset/I2C는 실제 controller·BPTWL·카메라·카드 MMIO·IRQ 상태를 사용한다. 정상/부재 slave·방향·repeated START/STOP·IRQ mask와 W1C, 재설정의 클럭/카드 경로 및 저장 상태 호환을 확인했다. 14.1 고정 레코드와 실제 slave 상태를 14.2로 재저장·복원하는 경우도 포함했다. JIT 설정으로 구동한 장치 fixture를 guest JIT 전송 실행으로 집계하지 않는다.

## 범위와 남은 조건

새 제품 소스 파일은 없다. 기존 그래픽/core fixture를 확장하며 AES 검증 파일 두 개와 이 릴리스 기록을 추가했다. 확인한 캡처의 미완료 읽기 분기, AES 소스, DSi의 해당 재설정/I2C 함수는 공식 기준에서 이어진 코드다. GPU 파일 전체가 상류와 동일하다는 뜻은 아니다.

저장 상태 형식은 **14.2**다. 14.1 이하 I2C 상태에는 전송 방향·STOP 상태가 온전히 남아 있지 않아, 새 START/STOP 또는 재설정까지 기존 허용 동작을 유지하고 이후에는 현재 규칙을 적용한다. 이 상태를 다시 저장해도 호환 모드를 보존한다. 기존 실행 파일은 14.2 저장 상태를 읽을 수 없으며, 기존 게임의 일반 저장 파일 형식은 바꾸지 않았다.

중간 접근 후 줄 단위 GL readback에는 비용이 들며 실제 게임 성능·전력 개선량을 주장하지 않는다. GR-05의 subscanline latch·VCOUNT 변경·실제 게임/실기, AD-14의 완전히 빈 요청·전송 중 제어 변경·정확한 busy/IRQ 시각, AD-17의 실제 NAND/firmware boot·NWRAM/DS·DSi mode 전환, AD-22의 전송 지연·warm-reset retention·실제 전원/음성/카메라 수락은 남는다. 공개 문서의 FIFO 태그 완료 순서는 프로토콜 해석이며 cycle 단위 실측값이 아니다.
