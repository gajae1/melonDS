# 1.1.30 — LAN mesh·상태 로드 오디오·캡처 소비

기준은 1.1.29(`1f7c3acb4c7b760bd171c197ae7b72112ff689ab`), 검증일은 2026-09-11이다. NP-02/FS-17, AD-05/CJ-20, CJ-19/GR-05/06을 독립 작성 후 통합했다. 원래 책임 버전 1.1.30의 성능 계측 목표나 공개 전체 계획의 완료를 뜻하지 않는다.

## 변경과 근거

**LAN:** 실제 loopback에서 참가자 세 명의 목록이 완성돼도 클라이언트끼리 프레임을 전달하지 못했다. 클라이언트는 임의 UDP 포트에서 듣지만 이전 mesh 구현은 고정 포트 7064를 사용했고 1.1.29의 새 목록 처리에는 mesh 연결이 빠졌다. 호스트가 관측한 포트를 기존 참가자 목록 뒤의 선택 확장으로 전달하고 IP만으로 서로 다른 peer를 합치지 않는다. 확장 지원 peer끼리는 높은 ID에서 낮은 ID로 한 연결만 만들며, 참가자 목록보다 먼저 온 미확인 연결은 거부한 뒤 제한된 간격으로 재시도한다. 새 클라이언트의 연결 완료는 현재 알려진 확장 지원 peer의 mesh 연결도 확인한다. 이미 게임 수신을 시작한 참가자는 늦게 연결된 peer에 준비 상태를 다시 알린다. 이탈·동일 ID의 새 endpoint에서는 오래된 peer·대기 프레임을 정리한다.

**오디오:** 성공한 상태 로드 뒤에도 이전 PCM 674개가 남아 다음 실제 callback에서 재생되는 반례를 생성 입력으로 확인했다. 성공 load/undo에서만 코어 출력 ring·blip 이력과 프런트엔드 필터·ramp를 초기화한다. 복원한 마지막 sample로 빈 resampler를 시작해 정상적인 상수 신호도 유지한다. guest clock·직렬화 sample·출력 rate/skew·volume·현재 cutoff는 보존한다. 사전 실패와 후반 실패 후 코어 복구는 기존 출력 이력을 유지한다.

**캡처:** 제품 코드 변경 없이 기존 생성 장면에 source A→DMA-first→warmed JIT 소비를 추가했다. 캡처를 끈 대조에서는 여덟 읽기가 모두 poison 값을 읽고, 캡처를 켠 다음에는 과거·미래 scanline에 맞는 빨강·초록·미변경 값이 나온다. 실제 ARM9 DMA가 첫 소비자이며 동일 JIT load 블록과 entry의 재사용을 확인한다. fastmem은 활성화했지만 VRAM 자체는 기존 동기화 경로를 통과한다. 직접 VRAM fastmem mapping이나 JIT가 DMA보다 먼저 읽는 수락으로 확대하지 않는다.

## 5페이즈와 검증

1. **재현:** LAN 다자간 전달과 성공 load의 PCM 반례를 기존 정상·실패 복구 대조와 함께 확인했다. 캡처는 이미 작동하던 경로의 검증 공백이었다.
2. **수정:** LAN은 통합 작성자, 오디오와 캡처는 각각 분리된 작업 공간에서 작성했다.
3. **통합:** 공유 CMake·실제 frontend load·기존 core/GL/SDL fixture를 순차 연결했다. 새 제품 소스 파일은 없다.
4. **검증:** 개별 LAN packet·실제 4명 loopback·Qt 연결, 오디오 4개 반례/대조와 기존 14개 회귀, 캡처 3개 backend와 기존 28개 장면을 통과했다. 최종 Windows x64 Release 전체 빌드 성공. v1 호환 수정 후 최종 소스의 CTest는 **555/555 통과, 실패 0, 건너뜀 0**, 병렬도 2에서 **55.33초**였다. 최종 application object로 생성 guest의 Qt 복구 경로도 통과했다. 별도 원본 LAN 상호 운용 시험은 아래와 같이 미통과 방향을 포함하며 CTest 통과 수에 섞지 않는다.
5. **배포:** 검증한 실행 파일·DLL/plugin·라이선스와 커밋된 소스를 버전별로 선별하고 manifest에 source commit·EXE·ZIP 해시를 연결한다.

## 호환성과 남은 조건

**LAN은 원본의 v1 handshake·discovery·참가자 구조·게임 패킷 형식을 유지한다.** 새 클라이언트는 ENet 접속의 부가 데이터에 포트 확장 지원 표시를 넣는다. 새 호스트가 이를 확인하면 기존 초기화 다음에 확장 승인을 보내고, 같은 reliable 채널로 참가자 목록 다음에 포트 정보를 전달한다. 지원 표시가 없는 구버전에는 기존 메시지만 보낸다. 구버전 호스트는 표시를 무시하며 새 클라이언트도 기존 방식으로 연결한다. 게임 패킷마다 버전을 협상하거나 추가 왕복을 넣지 않는다. 기존 비동기 처리·취소·패킷 경계 검사는 구버전 상대에서도 유지한다. 형식 호환과 실제 게임의 속도 향상은 다른 검증이다.

실제 ENet·별도 Windows 프로세스의 IPv4 loopback에서 1.1.29↔1.1.30은 호스트 역할을 바꾼 두 방향 모두 command·AID 3 reply·ack·timestamp가 일치했다. 포크 직전 원본 `8bdb579f`는 공식 [906e9ebb](https://github.com/melonDS-emu/melonDS/commit/906e9ebb27da8c6a715cd7abab4abfe8a8d29427)와 전체 tree가 같다. 이 원본 및 1.1.27이 호스트이고 1.1.30이 클라이언트인 조합도 통과했다. 각 revision의 LAN.cpp/h·MPInterface.h 원문을 그대로 별도 컴파일했으며 공식 배포 EXE나 게임 전체를 실행한 결과는 아니다.

**원본/1.1.27 클라이언트 방향은 이 환경에서 접속 실패가 남는다.** 같은 원본끼리도 실패했으며, ENet 밖의 일반 UDP 대조에서도 첫 패킷은 수신되지 않고 후속 패킷부터 도착했다. 원본 클라이언트는 첫 connect 하나를 보낸 뒤 5초 대기에서 끝났고, 새 비동기 경로는 재전송 후 연결됐다. 환경의 OS·driver·filter 중 원인 구성요소는 확정하지 않았다. 실패를 없애려고 원본 소스·timeout·네트워크 설정을 고치거나 warm-up 패킷을 넣지 않았다. 원본 클라이언트 방향의 상호 운용 수락은 통과로 세지 않는다.

신규 버전 4명 loopback은 늦은 참가·준비 통지·클라이언트 command/reply·ID 재사용·host 소실을 검증한다. 구버전이 섞인 3명 이상 mesh, 두 PC의 실제 게임, 방화벽·휴면·유실·장기 지연과 다른 OS 조합은 별도 수락이다. native layout의 다른 endian/ABI 호환성을 새로 보장하지 않는다. 원본에도 LAN 연결층이 있었으며 실제 게임의 로컬 무선 메뉴나 별도의 Wi-Fi 커넥션 설정을 우회하는 기능은 아니다. Netplay 메뉴는 활성화하지 않았다.

저장 상태 형식은 **14.2를 유지**한다. 오디오 검증은 생성 guest·실제 코어·실제 SDL callback thread와 dummy backend이며 청감·물리 지연의 수락은 아니다. 이미 OS/장치 버퍼에 제출한 소리를 회수하지 않으며 다음 callback과 이후 새로 생성한 PCM이 확인 경계다. 입력·마이크·RTC·외부 매체와 peer rollback 정책은 변경하지 않았다.

**설정 이관:** 원본과 1.1.27의 실제 Config.cpp가 생성한 TOML을 현행 로더로 읽고 저장한 뒤 별도 프로세스에서 재로드했다. 키 배정·명시적 해제·화면 값·음량·세이브 경로·알려지지 않은 확장 문자열이 보존됐다. 파일에 없는 설정의 기본값을 추가해도 기존 값은 유지했다. 오래된 INI의 가져오기와 손상 TOML의 덮어쓰기 방지는 기존 fixture가 담당한다. 기존 세이브의 소유 정보가 없으면 처음 게임을 열 때 기존 파일 사용/분리 선택이 나올 수 있다. 패키지에는 개인 설정·세이브를 포함하지 않는다.

**게임 저장·중간 저장 이관:** 원본 코어가 생성 DS를 실행하고 쓴 14.0 상태 파일을 원본과 현재 코어의 별도 프로세스에서 읽었다. RAM·CPU 레지스터·save를 복원하고 PC나 코드를 재설정하지 않은 채 ARM9 값 100→101, ARM7 값 37→38과 다음 프레임 완료를 확인했다. 원본이 내보낸 raw `.sav` 8,192바이트도 두 reader에서 전체 일치했다. 포맷 header나 section을 바꾸지 않았다. 이 결과는 생성 DS 한 카트의 core 경로이며 모든 게임·DSi·JIT·UI·모든 과거 버전의 수락은 아니다. 새 버전에서 만든 14.2 상태를 이를 지원하지 않는 구버전으로 되돌려 읽는 기능은 제공하지 않는다. 별도 Android 코어의 13.0 상태도 직접 호환되지 않는다.

캡처는 현재 Windows x64/NVIDIA GL driver에서 확인한 생성 장면이다. 다른 GPU·native A64·DS 실기의 capture timing·실제 게임·장기 실행은 남는다. 성능 향상이나 실기 전체 일치를 측정 없이 주장하지 않는다. [코드·계획·upstream 점검](../Audit_2026-09-11.md)에 추가 후보와 플랫폼 이식 경계를 기록했다.
