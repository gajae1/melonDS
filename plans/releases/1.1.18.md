# 1.1.18 — JIT 실행 권한·오디오 공급과 복구

상태: 구현·Windows 빌드·로컬 회귀 완료. 기준 1.1.17. CJ-04·AD-04·AD-08의 증분이며 기존 책임 버전 1.1.18의 DSi 부팅 과제 완료를 뜻하지 않는다.

## 5페이즈

1. **재현·계측:** 실제 ARM9 guest에서 허용된 코드를 컴파일한 뒤 실행 권한을 취소한다. 생산 오디오 callback의 공급 부족·복귀 파형, 코어 FIFO 덮어쓰기와 실제 SDL 출력 장치의 공급량을 관찰한다.
2. **원인 수정:** JIT 진입 시 현재 MPU 권한을 검사하고 ARM9 trace가 다른 권한 페이지를 합치지 않게 한다. 출력 callback 크기와 한 번에 생산하는 에뮬레이션 프레임의 크기를 구분한다.
3. **복구·보간 비교:** 부족한 오디오의 무음 전환/복귀에 짧은 ramp를 적용한다. SpeexDSP Q3의 고정 timer 합성 비교를 수행하되 변속·capture·채널 상대 지연 검증 전에는 통합하지 않는다.
4. **검증:** interpreter/JIT/fastmem의 예외 상태·부작용, 생성 PCM과 실제 장치 공급 측정, 전체 Windows CTest, 두 게임의 이전 코어 비교를 수행한다. 생성 입력·장치 전달·실제 청취를 구분한다.
5. **배포:** 버전별 Windows 실행 파일·소스와 공개 계획을 묶는다. 사용자 보고의 완전 해결, 청감 품질, 물리 지연이나 전체 MPU 지원으로 확대하지 않는다.

## JIT 실행 권한

허용 상태에서 생성한 ARM9 `MCR; B target` 블록을 재사용하며 target의 실행 권한을 취소하면, 기존 JIT는 금지된 target의 MOV/STR을 실행했다. 동적 BX는 기존 `JumpTo`에서 예외를 발생시켰고 interpreter도 정상이라, 정적 분기·cached block 경계로 원인을 좁혔다.

블록 진입 시 현재 `PU_Map`을 확인하고 기존 Prefetch Abort 경로를 사용한다. 다른 4 KiB 페이지의 정적 target을 블록 안에 합치지 않으며 순차 trace도 페이지 끝에서 종료한다. 생성 당시 MPU가 비활성이어도 이후 권한 변경 후 재사용할 수 있으므로 같은 경계를 적용한다. 전역 JIT 비활성화나 매번 전체 cache 초기화는 추가하지 않는다.

실제 생성 guest의 정상 cold/warm, 권한 취소 후 cached 정적 분기, 금지된 동적 분기, 재허용 5개 phase를 검사한다. 수정 전 interpreter는 5개를 통과하고 JIT/fastmem은 취소된 정적 분기만 실패했다. 수정 후 세 실행 모드 모두 통과하며 LR/SPSR/CPSR/PC와 target의 register·RAM 부작용 부재를 확인했다.

기대 권한과 exception 상태는 [ARM946E-S TRM DDI 0201D §2.3.8·4.2.3](https://documentation-service.arm.com/static/5e8e3ee588295d1e18d3aa82)와 [ARM ARM DDI 0100I §A2.6.5](https://documentation-service.arm.com/static/5f8dacc8f86e16515cdb865a)를 따른다. 같은 페이지 실행 중 권한 변경, 모든 data abort/writeback·Thumb fallthrough·겹친 region·TCM/cache·native A64·실물 pipeline timing은 후속 범위다.

## 오디오 공급·복구

`audioSync`는 한 SDL callback 분량보다 적게 남을 때까지 생산자를 기다리게 했다. 생산자는 한 에뮬레이션 프레임씩 진행하므로 callback이 backend에서 몰려 호출되는 낮은 버퍼 구성에서는 다음 프레임 생산을 늦추며 공급 부족을 만들 수 있다. 대기 기준을 선택한 callback 버퍼와 해당 프레임의 출력 샘플 수 중 큰 값으로 정한다. 출력 샘플 수는 현재 출력 clock과 실제 scanline 수로 계산한다. SDL 버퍼 설정이나 게스트 SPU 타이밍은 바꾸지 않는다. 이 조치는 host queue의 허용 선행량을 바꾸므로 물리 지연 감소를 의미하지 않는다.

기존 부족 처리에서는 부분 공급의 마지막 값을 반복하다가 빈 callback에서 즉시 0으로 바뀌고, 공급 재개 시 새 값으로 즉시 돌아왔다. callback 소유 상태로 약 1ms의 선형 전환을 적용한다. 연속 공급은 그대로 통과하고 명시적 mute는 즉시 무음이다. 추가 버퍼나 callback 안의 할당·로그는 없다. 이 ramp는 손실된 샘플을 복원하지 않으며 공급 원인 수정과 구분한다.

1000/-1000의 일정한 합성 입력에 부분 부족→빈 callback→재공급을 넣은 생산 callback 검사에서, 128/512 버퍼 모두 최대 인접 sample 변화가 수정 전 1000에서 수정 후 21로 줄었다. 기존 볼륨·filter·출력 범위 검사도 유지한다. 코어 FIFO는 실제 소비를 중단했을 때 덮어쓴 frame 수를 계수하며 drain 뒤에도 누적값을 보존한다. 이 진단값은 savestate에 저장하지 않는다.

`MELONDS_AUDIO_DIAGNOSTICS=1`을 설정해 실행하면 pause/종료 시 누적 callback 요구·공급·부족/빈 횟수, read 구간 최대 시간, callback 시작 간격 최대값, FIFO 덮어쓰기·잔량을 로그에 남긴다. 기본은 비활성이며 callback 내부에서는 로그를 출력하지 않는다. 간격은 물리 출력 지연이 아니고 덮어쓰기 계수는 모든 종류의 audio drop을 의미하지 않는다. 장치 이름·개인 경로는 이 로그에 포함하지 않는다.

실제 장치 검사는 기존 ROMSmoke에 선택적으로 연결한 생산 callback·sync를 사용한다. 출력 장치에 제출하기 직전 PCM을 무음으로 바꾸므로 이것은 청취 검사가 아니다. 60 FPS의 프런트엔드 delay/error 정책을 사용하지만 Qt 이벤트·화면 presentation은 빠져 있다. [SDL의 실제 spec·callback thread 계약](https://wiki.libsdl.org/SDL2/SDL_OpenAudioDevice)에 따라 장치가 열려 반환한 값을 기록하고 pause 뒤 통계를 읽는다.

## sinc 비교와 채택 판정

후보는 [SpeexDSP 1.2.1의 Q3 resampler](https://github.com/xiph/speexdsp/blob/1b28a0f61bc31162979e1f26f3981fc3637095c8/libspeexdsp/resample.c) 하나다. BSD 3-clause 원 구현의 실제 로컬 DLL을 사용했고 새 의존성을 제품에 추가하지 않았다. 채널별 source→mix 보간을 현재 최종 혼합 출력의 blip_buf 변환과 구분한다.

고정 timer의 선택한 downsample tone에서 Q3 alias는 입력 tone 대비 −94.84dB였다. 측정한 impulse 지연은 0.73~1.47ms이며 모든 timer의 상한이 아니다. 16개 독립 채널의 bulk 처리 비용은 신호 1초분당 1.76~14.65ms였다. 이는 별도 native DLL 처리량이고 실제 SPU의 한 mix tick 호출 비용이나 FPS 향상이 아니다. 기존 None/Linear/Cubic 비교는 생산 함수를 실행한 것이 아니라 고정 timer 산술을 옮긴 모델이다.

**이번에는 채택을 보류한다.** 게스트 timer 변경 시 과거 sample의 시간 간격, 시작/loop/상태 복원, guest capture에 미치는 변화, 다른 timer 채널 사이 상대 지연, 실제 tick 비용과 청취가 미검증이다. 다음 비교는 같은 후보를 실제 채널 경계에 연결한 최소 실험으로 한정한다. 새로운 보간 메뉴나 기본값 변경은 하지 않는다.

## 최종 실행 기록

한 DS 게임의 같은 생성 입력·software renderer·3600프레임을 실제 WASAPI 48kHz 장치에서 각 조건 한 번씩 비교했다. 같은 callback/ramp/MPU 소스에서 동기화 기준만 바꾼 전후 비교다. 장치가 반환한 버퍼는 요청과 같은 128/512였다.

| 버퍼 / 보간 | 기존 공급 부족 frame / callback 횟수 | 수정 공급 부족 frame / callback 횟수 | 기존 → 수정 paced FPS |
|---|---:|---:|---:|
| 128 / None | 576,003 / 5,400 | 3 / 1 | 49.997 → 59.990 |
| 128 / Cubic | 576,003 / 5,400 | 1,174 / 13 | 49.992 → 59.962 |
| 512 / None | 739 / 5 | 1,488 / 12 | 59.984 → 59.966 |
| 512 / Cubic | 387 / 4 | 579 / 4 | 59.986 → 59.989 |

8회 모두 실행 유지·같은 최종 framebuffer digest·코어 FIFO 덮어쓰기 0이었다. 128 조건의 반복적인 생산 정체는 줄었지만, 512 조건은 이번 단회 측정에서 공급 부족량이 오히려 늘었다. 따라서 모든 버퍼의 개선이나 무잡음을 주장하지 않는다. 드문 부족의 발생률·청감과 추가 queue 선행량의 물리 지연은 후속 측정이 필요하다. 측정 중 별도 빌드/게임 부하는 실행하지 않았으나 OS scheduling과 외부 host 부하는 고정하지 않았다.

최종 Windows x64 프런트엔드 빌드와 전체 CTest **388/388, skip 0, 병렬8에서 12.09초**를 확인했다. UCRT64 GCC 16.2.0·Qt 6.11.2·SDL 2.32.10, C23/C++26·Release·JIT·OpenGL/Compute 구성이다. 실제 GPU frame capture와 기존 입력 설정 회귀를 포함한다.

두 DS 게임을 각 3600프레임씩 현행 interpreter/JIT/fastmem과 1.1.17 interpreter/JIT에 같은 입력으로 실행했다. 총 10회가 종료 0·실행 유지였다. 첫 게임은 각 모드의 이전 화면과 같고 기존 interpreter/JIT 차이는 남는다. 두 번째 게임은 현행 세 모드가 이전 interpreter와 바이트까지 같으며, 이전 JIT와의 차이는 소개 대화창 넘김 표시의 29픽셀에 한정됐다. 두 버전 모두 정상 소개 화면임을 확인했다. 이 최종 화면 비교는 전체 상태 동등성·게임 전체 호환성이나 실기 타이밍 수락이 아니다.

게임 비교의 실행 시간도 기록했으나 두 작업의 병렬 실행과 cold 시작 비용을 통제한 성능 benchmark는 아니다. JIT 페이지 제한의 전체 성능 향상/회귀율은 확정하지 않는다. CJ-08 장치 이벤트, 전체 오디오 장치 복구/지연과 앞선 미완료 과제를 유지한다.
