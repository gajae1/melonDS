# 1.1.21 — GL 할당 실패·context 반환 동기화

상태: Windows 구현·로컬 회귀와 게임 대조 확인. 기준 1.1.20, 검증일 2026-09-10. GR-07·GR-11/12의 실제 증분이며 책임 버전 1.1.21의 DSP 과제 완료를 뜻하지 않는다.

## 5페이즈

1. **근거·재현:** 정상 배율과 장치 한도·실제 할당 오류를 대조한다. context 생성·현재화·파괴 thread를 소스에서 연결하고 도달 가능한 반환 신호 순서를 재현한다.
2. **최소 수정:** 크기 계산 전에 지원 범위와 장치 한도를 검사한다. 첫 할당 오류에서 중단하고 설정 실패를 반환한다. context 통지는 실제 상태와 같은 mutex로 연결한다.
3. **통합:** 프런트엔드의 실제 renderer·오류 통지·재선택과 pending 캡처 보존을 연결한다. 기존 설정 저장 선호와 context 소유권을 구분한다.
4. **검증:** 실제 GL 할당 오류·제한 조회 주입·OOM 모의를 구분한다. 생성 캡처 보존·소프트웨어 프레임·정상 재선택, 결정적인 thread 순서와 전체 Windows 회귀·같은 게임 프레임을 확인한다.
5. **배포:** 검증한 결과만 실행 파일·소스·공개 계획에 반영한다. 실제 메모리 고갈·surface 상실·다중 창·다른 driver/OS/native A64와 앞선 미완료 항목은 남긴다.

## GL 설정·할당 실패

기존 배율 변경은 요청 크기와 장치 한도를 대조하지 않고 기존 저장 영역을 재할당했다. Compute buffer/texture 할당이 실패해도 나머지 할당을 계속하고 설정 성공 상태를 유지했다. 실제 driver의 `GL_INVALID_VALUE`로 buffer 또는 immutable texture 할당을 실패시켰을 때 각각 추가 Compute 할당 8회/2회와 미처리 오류가 남았다.

설정 적용은 이제 bool 결과를 반환한다. 1..16 범위를 먼저 확인하여 잘못된 값의 signed 크기 계산을 막고 texture/viewport 한도를 조회한다. 화면은 256×192지만 캡처 viewport는 256×256이므로 더 큰 높이도 반영한다. Compute는 가장 큰 SSBO의 byte 크기와 RGBA16UI texture buffer의 texel 수를 별도로 대조한다. SSBO 한도는 `glGetInteger64v`로 조회한다. [Khronos SSBO 명세](https://raw.githubusercontent.com/KhronosGroup/OpenGL-Registry/main/extensions/ARB/ARB_shader_storage_buffer_object.txt), [GL 상태 조회](https://raw.githubusercontent.com/KhronosGroup/OpenGL-Refpages/main/gl4/glGet.xml).

공통 capture/output, 2D 색·깊이, classic 3D, Compute buffer/texture 할당에서 오류를 확인하고 첫 실패에서 해당 설정 적용을 중단한다. 재할당 전 기존 캡처를 보존한 뒤 실패를 프런트엔드에 전달한다. 프런트엔드는 실제 software renderer를 생성하고 기존 소프트웨어 설정을 적용하며 활성 renderer 상태·오류 통지 1회를 맞춘다. 반복 update는 실패한 GL renderer를 계속 재시도하지 않는다. 명시적 재선택은 정상 조건에서 다시 초기화·컴파일·프레임 진행을 할 수 있다. ROM smoke도 설정 실패를 반환한다.

`GLAllocationFailure`는 정상 1x→2x, texture/viewport/SSBO/texel 제한, 잘못된 배율, 실제 buffer/texture·공통 캡처·2D depth·classic depth 오류, 모의 OOM의 12개 case를 사용한다. 초기 정상 프레임 후 실제 source-B 캡처를 GPU에 남기고 실패시킨다. 대체 renderer에서 캡처 픽셀이 보존되고 RAM 프레임을 생산하는지 확인한다. 정상/재선택의 GL 출력은 실제 texture 존재·크기와 프레임 진행을 확인하며 픽셀 정밀도는 기존 독립 readback 회귀로 검사한다. 설정 읽기·OSD를 격리한 현재 생산 `updateRenderer` 메서드 검사이며 전체 Qt 창 테스트가 아니다.

실패 안내와 실행 중 renderer 전환은 적용하지만 저장된 선호 renderer/배율은 유지한다. 따라서 설정창의 선택값이 실행 중 fallback과 다를 수 있다. 1.1.19의 shader 실패도 같은 정책이다. 사용자 선호를 덮어쓰는 정책 변경이나 설정창의 실시간 활성 상태 표시는 이번 증분에 포함하지 않는다.

한도 주입은 작은 작업량으로 판정 분기를 재현한 것이며 실제 장치 한도가 그 값이라는 뜻이 아니다. OOM은 할당을 생략하고 오류를 주입한다. 물리 VRAM을 고갈시키지 않는다. [Khronos glBufferData](https://raw.githubusercontent.com/KhronosGroup/OpenGL-Refpages/main/gl4/glBufferData.xml)는 할당 실패를 정의하고, [glGetError](https://raw.githubusercontent.com/KhronosGroup/OpenGL-Refpages/main/gl4/glGetError.xml)는 실제 OOM 뒤 GL 상태 보존을 보장하지 않는다. 따라서 코어 software 복구를 손상된 GL 표시 context의 완전한 회복으로 확대하지 않는다. 실장치 OOM·OS context 재생성은 GR-11 후속이다. 모든 배율의 indirect dispatch 상한·작은 VRAM 장치·CPU 메모리 고갈·할당 전 peak 사용량도 별도 검증으로 유지한다.

## Context 호출·반환 경계

현재 frontend에서 `Context::Create` 호출은 GUI thread에 모인다. worker가 동시에 이 함수를 호출한다는 원래 후보는 뒷받침되지 않아 creator끼리만 잠그는 mutex를 추가하지 않는다. 다만 새 인스턴스 생성의 전역 GLAD 재로딩과 기존 worker의 GL 읽기는 겹칠 수 있다. deinit 응답 뒤 paused 표시 루프의 panel 재접근 경로도 남아 있다. 이는 소스로 확인한 도달성이며 실제 surface 오류·driver crash 발생률을 측정한 결과가 아니다.

별도로 기존 `borrowGL`은 worker가 GL을 놓고 완료 semaphore를 알린 뒤 조건변수 대기를 시작했다. UI가 그 사이 `returnGL`을 끝내면 통지를 잃고 worker가 다음 반환을 기다릴 수 있었다. [Qt QWaitCondition](https://doc.qt.io/qt-6/qwaitcondition.html)의 통지는 아직 대기하지 않는 thread를 위해 저장되지 않는다.

같은 mutex로 보호하는 `glBorrowed` 상태를 완료 알림 전에 설정한다. worker는 이 값이 true인 동안만 기다리고, UI의 반환은 값을 false로 만든 뒤 깨운다. 기존 직렬 UI의 한 borrow/return 쌍을 유지하며 중첩 대여 기능을 추가하지 않는다.

`GLBorrow`는 현재 생산 handler에서 다른 메시지 case만 제외하고 borrow case·완료 알림·wait tail, public borrow/return 메서드와 header 상태 선언을 그대로 추출한다. 실제 Qt mutex/조건변수/두 thread를 사용하며 GL release는 관찰용 대역이다. 완료 알림 직후 barrier로 worker를 멈추어 UI 반환을 먼저 끝내는 case와 실제 대기 진입 후 반환하는 정상 대조를 실행한다. 수정 전 early case만 실패했고 정리용 두 번째 반환이 필요했다. 수정 후 early는 추가 대기 0, waiting은 정상 대기 후 복귀하여 두 case 모두 정리용 반환 없이 통과했다. 예상 실패를 timeout이나 확률적 반복으로 판정하지 않는다.

이 수정은 반환 신호의 수명 문제를 해결한다. 실제 shared context 생성·native DoneCurrent·panel 교체·다중 창의 전체 소유권, GLAD 재로딩 동안 모든 worker 정지는 다음 GR-11/12 과제로 남긴다.

## 통합 검증

- Windows x64 Release, GCC 16.2, Qt 6.11.2, SDL 2.32.10, C23/C++26. JIT·OpenGL/Compute와 기존 runtime ISA dispatch 구성의 전체 frontend 빌드 성공.
- 전체 CTest **417/417, skip 0**, 26.21초. 실제 GPU 오류 처리·캡처 보존·정상 픽셀 회귀와 두 Qt 반환 순서를 포함한다.
- 두 비공개 DS 게임을 fastmem으로 software/OpenGL/Compute 각각 3,600프레임 실행했다. 6개 최종 프레임 모두 같은 게임·입력·renderer의 기존 1.1.20 결과와 바이트가 일치한다. 같은 이미지의 이전 시각 확인을 재사용하며 장기 게임 수락이나 모든 renderer 간 동등성으로 확대하지 않는다.
- 초기화·설정 경계의 오류 확인이며 매 프레임의 검사나 보간/오디오 기본값 변경을 추가하지 않는다. 전체 FPS·메모리 절약량·물리 지연 개선 수치는 측정하지 않았다.

실행 파일은 `1.1.21-melonDS.exe`, 배포 ZIP은 `1.1.21-melonDS-windows-x64.zip`과 `1.1.21-melonDS-source.zip`이다. 실행 파일·필요 DLL/plugin·라이선스만 선별하며 게임·설정·저장 데이터를 포함하지 않는다.
