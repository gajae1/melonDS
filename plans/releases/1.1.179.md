# 1.1.179 — x64 JIT 조건 건너뛰기 점프 잘림 수정, 저장 상태 이력 정규화, 보간 뱅크 로딩

2026-09-25. 이전 버전은 1.1.178이다. 기본 배포는 SDL2이고 SDL3는 `ENABLE_SDL3=ON` 선택형 빌드다.

x64 JIT이 조건부 명령을 건너뛰는 점프를 2바이트 `jcc rel8`로 내던 문제를 고쳤다. 명령 본문이 127바이트를 넘으면 릴리스 빌드에서는 경고만 찍고 변위를 잘라, 점프가 본문 중간으로 떨어졌다. Pokemon Black에서 fast memory를 켠 채 JIT 캐시를 비우면(저장 상태를 불러올 때마다, 또는 코드 버퍼가 가득 찰 때) 다음 프레임에 ARM7 `ldreq pc,[r1],#4`의 134바이트 본문에서 이 문제가 드러나 "this is a JIT bug"로 종료했다(0xC0000409). fast memory를 끄면 종료 대신 잘못 실행됐다. 조건 건너뛰기는 이제 항상 rel32 점프를 쓰고, 블록 종료 시퀀스(더티 레지스터 저장과 tail call)를 건너뛰는 나머지 네 곳도 rel32로 바꿨다. x64 JIT의 rel8 점프 25곳을 모두 감사한 결과 남은 곳의 본문 상한은 71바이트 이하이고, 계측 빌드로 두 게임 24개 실행 조합(fast memory 켜고 끔, 블록 크기 1/16/32, 1200프레임에서 JIT 리셋 후 2400프레임)과 core 검사 150개를 돌리는 동안 넘침은 0건이었다. 앞으로 넘침이 생기면 코드 생성기가 거리를 출력하고 즉시 중단한다. 새 `core-*-cond-transfer-reach` 검사는 1.1.178에서 fastmem이 비정상 종료하고 jit이 상태가 달랐으며, 수정 후 인터프리터·jit·fastmem 모두 통과한다. Black은 fast memory와 1200프레임 JIT 리셋으로 2400프레임까지 정상 실행된다. ARM64 JIT은 이번 수정 범위 밖이다.

BV-17 저장 상태 정확 일치 조사에서 Solatorobo의 남은 두 차이를 해결했다. 비활성 카트 ROM 전송 이벤트의 지난 마감 시각과 비어 있는 GPU 3D 명령 FIFO의 커서·지난 칸은 이후 동작이 읽지 않는 이력이지만 JIT 리셋 경로에 따라 값이 달랐다. 저장할 때만 이 둘을 고정된 표현(시각 0, 빈 FIFO 초기 상태)으로 기록하고, 실행 중인 상태와 다른 이벤트·주기 시계·SPI 완료 시각·점유된 FIFO는 그대로 둔다. 저장 형식과 버전은 바뀌지 않고 옛 저장 파일도 읽힌다. 12,000프레임 연속 실행과 6,000프레임 저장·JIT 리셋·복원 경로의 최종 저장 상태가 이제 바이트 단위로 같다. 새 `savestate-canonical-history` 검사는 이 이력의 정규화, 살아 있는 상태의 보존, 옛 FIFO 이력 읽기, IPC FIFO의 기존 언더플로 동작을 확인한다. Black은 fast memory를 끈 JIT에서 캐시 리셋 뒤 실행이 캐시된 실행과 달라지는 별도 차이(RAM 1바이트, SPI 이벤트 시각, SPU 상태)가 남아 **BV-17 수락은 여전히 미완료**다.

오디오 보간 뱅크 로더는 곧 모두 덮어쓸 계수 저장소(두 주파수 합계 약 98MB)를 먼저 0으로 채우지 않는다. 계수 계산과 읽기 순서는 같고, 전체 계수표 덤프의 해시가 같다. 뱅크 생성은 40.3ms에서 33.4ms로(9/9쌍), 시작 구간은 약 5.7ms 짧아졌다.

같은 라운드에서 ARMv5 JIT 실행 루프 정리(명령 53→50개, Black 1.05% < 잡음 1.24%, Solatorobo 1.13% 느림), Software 3D 스캔라인의 스팬별 특수화(2.7% 느림 또는 잡음 안), 최소 위상 Read 희소 꼬리 구조 변경(조밀 입력 3~5% 느림)은 채택하지 않았다. 프로파일의 `ucrtbase`·`NtReadFile` 표본은 대부분 시작 시 ROM 적재와 여러 호출자에 흩어진 작은 복사여서 고칠 대상이 없었다.

비공개 게임 두 개의 헤드리스 Software 1200프레임 ABBA 실행에서 1.1.178과 1.1.179의 최종 화면·누적 PCM·프레임버퍼 digest가 같았다.
