# 1.1.130 — Vulkan readback 메모리 선택과 pipeline cache

2026-09-16. 기준은 로컬 1.1.129 `a3b7880d`다. 중단 시 원격은 1.1.128이었고,
이번 작업에서 1.1.129의 전체 로컬 빌드와 CTest 960/960을 다시 확인한 뒤 원격 master에 반영했다.
이 릴리스는 GR-14/15·BV-07의 후속이며 전체 로드맵이나 실기 정확성 완료 선언이 아니다.

## 구현

Vulkan 결과 회수용 버퍼만 HOST_CACHED를 우선 선택한다. HOST_VISIBLE와 HOST_COHERENT,
해당 버퍼의 memoryTypeBits 조건은 필수로 유지한다. 캐시 가능한 종류가 없으면 기존 호환 종류를 사용한다.
선호 종류의 메모리 부족 오류에서는 기존 호환 종류가 다른 경우 한 번 재시도한다.
DEVICE_LOST 등 다른 오류는 숨기지 않는다. 성공 전 임시 핸들을 소유 멤버로 게시하지 않는다.
일반 upload staging의 선택 순서, GPU→CPU memcpy, host-read barrier/fence와 재사용 CPU 버퍼는 유지한다.
비일관성 메모리를 새로 허용하거나 미완료 GPU 메모리를 직접 span으로 노출하는 변경이 아니다.

VkPipelineCache는 Device가 필요할 때 한 번 생성하고 같은 장치의 pipeline 재생성에 재사용한다.
장치의 기존 렌더링 스레드 소유권을 따르며 디스크 파일·기기 간 공유·영구 캐시는 만들지 않는다.
캐시 생성의 메모리 부족은 최적화만 비활성화하고 uncached 렌더링을 유지한다. 다른 오류는 전파한다.
장치 해제 시 캐시를 해제한다. 드라이버가 보관하는 캐시의 상주 메모리 비용은 별도로 측정하지 않았다.

해상도 콤보 도움말을 실제 1~16배 표시와 native capture 구분에 맞게 수정했다.
TOML char8_t literal의 deprecated 공백 두 곳을 제거하고, Teakra가 상위 CMake의 진단 설정을
deprecated 변수로 덮어쓰지 않도록 했다. 의존성 버전·DSP 동작·컴파일러 최적화 플래그를 바꾸지는 않았다.
게스트 CPU/DMA 타이밍, SPU PCM·보간 계수, 저장상태 형식, 셰이더 수식·512개 배율 variant는 변경하지 않았다.

## 메모리 선택 측정

동일 Windows/GCC16.2/C++26/-O3/-fwrapv와 RTX 5080에서 1.1.129 라이브러리와 메모리 선택 수정본을 비교했다.
clear frame 40회 평균에는 GPU 렌더링/결과 회수와 전체 RGB6/A5 변환, native 원점 조회·전체 checksum 소비가 포함된다.
1/3/8배 각각 준비 1쌍을 제외한 7쌍을 순서 무작위화하여 측정했고 모든 실행을 같은 논리 CPU에 고정했다.
총 48개 실행(준비6+측정42)의 짝별 checksum은 모두 일치했다. 측정 중 다른 빌드나 GPU 테스트를 실행하지 않았다.

| 배율 | 기준 중앙값 | 캐시 우선 중앙값 | 해당 합성 workload 시간 감소 |
|---|---:|---:|---:|
| 1x | 1.314050 ms | 0.350737 ms | 73.31% |
| 3x | 4.987987 ms | 0.735930 ms | 85.25% |
| 8x | 35.180815 ms | 2.614790 ms | 92.57% |

복잡한 폴리곤/텍스처의 실제 게임 FPS, 프레임 전체 지연 또는 다른 GPU의 성능 수치가 아니다.
CPU 주파수는 고정하지 않았다. 이 결과는 GPU mapping을 직접 읽는 이전의 기각된 후보와 구분한다.
이번에도 CPU 캐시 메모리로 memcpy한 뒤 소비한다. 실제 장치의 선택 종류는 default=2, cached=3이었다.
기존 호환 메모리로 fallback하면 이 성능 이득까지 유지된다고 보장하지 않는다.

## Pipeline cache 사전 측정과 제품 검사

별도 실험기에서 실제 vkCreateComputePipelines에 캐시를 전달한 경우와 null을 비교했다.
같은 Device에서 6회 생성 중 첫 회를 제외하고, 1/8배 각각 순서를 바꾼 7쌍을 측정했다.
전체 pipeline 생성자 중앙값은 1x 7.682→7.187ms, 8x 10.483→10.190ms였다.
그중 vkCreateComputePipelines 합은 1x 2.527→1.987ms, 8x 2.485→2.096ms였다.
이는 prototype의 반복 생성 결과이며 cold 앱 시작·게임 실행속도·실제 설정창 지연의 개선율은 아니다.
전체 초기화 이득은 작고 드라이버별 차이가 있을 수 있다. 제품 경로의 수명·결과 일치는 별도 회귀로 검사했다.

## 미완료 작업을 분리

clear color/depth 업로드의 두 제출·대기를 한 번으로 묶는 시험은 현재 코드에서 제출2회로 실패했다.
관련 제품 구현 쓰기가 도구 단계에서 차단돼 적용하지 않았다. 미사용 선언과 실패 시험은 기본 빌드에서 제거하고
`build/evidence/continue-1.1.130/unapplied-clear-pair/`에 반례를 보존했다. 실제 UploadClearBitmap은 아직 두 동기 호출이다.

## 실행 검증과 경계

Windows x64 / CMake4.4.3 / GCC16.2.0 / C23·C++26 / LTO OFF에서 전체 기본 빌드가 성공했다.
캐시/메모리 구현과 TOML·Teakra·해상도 도움말 변경을 포함한 전체 CTest는 **962/962, 실패0·skip0**(171.81초)다.
같은 구성의 회귀 전체이며 다른 OS/ISA·상용 게임 전체·DSi 실기를 의미하지 않는다.

메모리 선택의 RED는 `cached readback memory not preferred`였고 수정 후 통과했다.
실제 Vulkan allocation 관측에서 default type2/cached type3 및 주입한 OOM의 원래 coherent type 재시도를 확인했다.
DEVICE_LOST 주입은 실제 장치를 잃게 만든 것이 아니라 반환 오류를 시험 대역으로 바꾼 것이며, 재시도 없이 전파됐다.
Pipeline cache RED는 `creates=0, pipelines=64, cached=0`으로 실패했다.
수정 후 같은 Device의 두 pipeline 생성은 캐시1개/64개 pipeline을 재사용하고 전체 화면 바이트가 일치했다.
선택적 cache OOM에서는 캐시 없이 두 프레임을 정상 생성했고, 다른 오류는 pipeline 생성 전에 전파했다.

전체 검사 후 발견된 세 파일의 동작 보존 경고 정리도 빌드했다.
`Screen.cpp`는 implicit this capture를 `[this]`로, FrontendInput fixture는 저장 키코드 비교의 int 변환을 명시적으로,
DSiSDTransfer fixture는 중복 WIN32_LEAN_AND_MEAN을 조건부 정의로 바꿨다. 재빌드 로그의 경고는0이었다.
이 세 변경 뒤 선택한 영향 검사 재실행 요청은 도구 단계에서 차단되어 실행하지 못했다.
962개 결과는 그 직전 코드에 대한 것이며, 마지막 표기 정리는 컴파일·diff 검토까지다. warning-free 전수 빌드로 일반화하지 않는다.

최종 라이브러리로 재빌드한 무음 AudioOutput 검사에서 SDL/WASAPIShared × 요청128/512의 4조건이 통과했다.
48kHz, SDL period128/512, WASAPIShared period480/480을 관측했다. 정지 중 source callback이 늘지 않고 재개 후 다시 진행했다.
물리 스피커 지연·게임 청취·장기 공급·장치 탈착을 확인한 결과는 아니다. 오디오 제품 소스는 이번에 바꾸지 않았다.
