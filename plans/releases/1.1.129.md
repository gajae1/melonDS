# 1.1.129 — 렌더링 임시 메모리와 전송 비용

2026-09-16. 기준 소스 `739ec2eb`(1.1.128). GR-14/15·BV-04/07의 후속 작업이다.
전체 로드맵 완료나 실기 정확성 인증을 의미하지 않는다. Vulkan의 1~16배 지원은 유지한다.

## 구현과 재현

OpenGL Compute의 색/깊이/속성 임시 버퍼는 MaxWorkTiles 대신 실제 MaxBatchWork만큼 할당한다.
정렬된 work descriptor의 shader offset은 기존 MaxWorkTiles를 유지하므로 그 저장소를 임의로 줄이지 않았다.
배율 지원 검사는 축소된 scratch뿐 아니라 영구 7-layer 출력·span 저장소의 크기를 함께 검사한다.
기존 split-batch 시험에 실제 GL 버퍼 크기 검사를 추가하여 실패→통과를 확인했다.
1536 work로 제한한 시험의 세 임시 버퍼는 각각 3,145,728→393,216 bytes다. 색/깊이/그림자 분할 결과도 동일하다.
추가 8배/SSBO 한도 128MiB 모의 조건은 과도한 기존 예상량 때문에 거절됐고, 실제 필요한 크기로 검사한 뒤 통과했다.
이것은 해당 한도를 가진 모든 물리 GPU의 실행을 보장하지 않는다.

Vulkan UploadImage는 fence 완료를 유지하면서 staging 버퍼를 재사용한다. 필요할 때만 커지며 할당 실패 시 기존 버퍼를 보존한다.
같은 크기 12회 업로드, 확장 실패 뒤 작은 재시도, 확장 후 8회 업로드의 추가 버퍼 생성 수는 12/1/8→0/0/0이다.
RenderView는 재사용하는 CPU 캐시 메모리를 반환한다. 호출자는 다음 render 시도나 pipeline 파괴 전에 소비한다.
기존 Render는 독립 소유 vector를 계속 반환한다. 제품 DrawFrame은 borrowed view를 즉시 소비한다.
GPU readback→CPU의 memcpy와 host-read barrier/fence는 유지한다. 제품 경로에서 매 프레임 vector를 새로 할당/초기화하지 않도록 한 변경이다.
최대 크기 staging과 현재 해상도의 CPU readback 버퍼는 pipeline 수명 동안 유지되는 메모리 비용이 있다.

## 채택하지 않은 후보

GPU mapping을 직접 span으로 노출하는 후보는 전체 색 변환·native 원점 조회까지 측정했을 때 더 느렸다.
1/3/8배에서 약 0.727/3.286/29.023ms→5.652/15.006/78.869ms로 악화되어 제품에서 제거했다.
픽셀 일부만 읽은 초기 측정은 실제 소비 비용을 반영하지 못해 성능 근거에서 제외했다.
HOST_COHERENT는 HOST_CACHED를 보장하지 않는다. 결과의 byte 일치와 성능 적합성은 별도로 확인해야 한다.

## 전후 측정

동일 GCC16.2 / C++26 / -O3 -fwrapv. 기준 ComputePipeline 소스와 수정본을 별도 실행 파일로 빌드했다.
1/3/8배 각각 준비 1쌍을 제외한 7쌍을 순서 무작위화하여 측정했다. 최종 측정 중 다른 빌드/GPU 검사는 실행하지 않았다.
각 업로드는 100회 평균이며, 렌더링은 clear frame 40회와 전체 RGB6/A5 변환·native 원점 조회·checksum 소비를 포함한다.
렌더링 수치는 폴리곤이 복잡한 실제 게임 FPS가 아니다. CPU affinity/frequency는 고정하지 않아 작은 차이는 재측정이 필요하다.

| 조건 | 이전 중앙값 | 수정 중앙값 |
|---|---:|---:|
| 8×8 업로드, 1배 pipeline | 230.428 us | 57.443 us |
| 256×256 업로드, 1배 pipeline | 268.210 us | 79.828 us |
| 1배 clear/readback/색 변환 | 0.738267 ms | 0.722547 ms |
| 3배 clear/readback/색 변환 | 3.298425 ms | 2.970625 ms |
| 8배 clear/readback/색 변환 | 29.263362 ms | 28.349915 ms |

세 배율의 업로드 시간 감소는 약70~76%다. readback 합성 시험의 작은 개선을 전체 게임 개선율로 확대하지 않는다.
48개 실행은 준비 6개와 측정 42개로 나뉘며 짝별 전체 소비 checksum은 모두 일치했다.
GPU→CPU 복사 자체를 없애거나 제출 대기를 비동기화한 결과가 아니다.

## 미적용과 후속 경계

readback에서 HOST_CACHED를 우선 요청하고 coherent 메모리로 fallback하는 별도 후보는 도구 판정으로 적용되지 않았다.
그 후보의 순수 메모리 선택 테스트/실패 로그는 build/evidence에 보존하고 제품과 기본 테스트 등록에는 남기지 않았다.
Teakra의 CMake 진단 변수, TOML UTF-8 literal 공백, 오래된 해상도 .ui 도움말을 고치는 요청도 차단돼 미적용이다.
이 항목들의 정리를 완료했거나 warning-free라고 하지 않는다.

실기와 다른 native 화면의 최초 차이, Vulkan GPU 2D/capture·직접 GPU 표시, staging 묶음 제출, pipeline cache는 별도 후속이다.
오디오의 PCM·필터·Minimum-phase 계수는 변경하지 않았고 장기 청취/물리 지연/탈착 수락을 자동 승격하지 않는다.
동기화 근거: https://docs.vulkan.org/spec/latest/chapters/synchronization.html
메모리 속성 근거: https://docs.vulkan.org/refpages/latest/refpages/source/VkMemoryPropertyFlagBits.html

## 최종 로컬 검증

Windows x64 / CMake4.4.3 / GCC16.2.0 / C23·C++26 / LTO OFF에서 전체 기본 빌드 타깃이 성공했다.
수정 후 전체 CTest는 **960/960 통과, 실패0·skip0**(117.79초)다. 선택한 일부 검사만의 숫자가 아니다.
단, 이 구성에 등록된 Windows 테스트 전체이지 다른 OS/ISA/실기/모든 상용 게임을 포함하는 것은 아니다.
초기 전체 실행은 948개 통과, 오래된 asset-reset 기대값1개 실패, GL loader 미빌드11개 미실행이었다. 이 기록은 보존했다.
GL loader는 실제 renderer 선언 및 새 Native panel 인터페이스를 사용하는 대역으로, CaptureReadback은 실제 읽은 바이트와 계측 바이트를 비교하도록 복구했다.
asset-reset 기대값은 1.1.125의 정책과 충돌했다. 완료된 바이트를 새 경로로 자동 재기록하지 않는 제품 보호 코드는 그대로 유지했다.
테스트는 새 경로 파일 미생성, 기존 파일과 RAM 보존, 이후 새 guest 쓰기가 새 경로에만 커밋되는 것까지 검사한다.
관련17개 검사와 전체 재실행에서 통과했으며 SaveManager/EmuInstance 제품 저장 코드는 바꾸지 않았다.

별도로 실제 Windows 기본 endpoint를 product AudioOutput 라이브러리로 무음 시험했다.
SDL 및 WASAPIShared 각각 요청128/512의 Open→Start→Stop→Resume→Close 4조건이 통과했다.
모두48000Hz이며 SDL 실제period128/512, WASAPI 실제period480/480이다. callback period를 물리 출력 지연으로 취급하지 않는다.
이번에는 실제 게임 청취·장기 재생·물리 탈착·DSi 기기 비교·Vulkan validation layer를 실행하지 않았다.

앱 --help는1.1.129이며 검증 로그·JUnit·전체 테스트 목록·전후 벤치 원자료는 `build/evidence/costs-1.1.129/`에 보존한다.
Actions와 macOS 빌드, 개인 ROM/BIOS/NAND/저장 파일 사용은 하지 않았다. 다른 작업트리 파일은 유지했다.
