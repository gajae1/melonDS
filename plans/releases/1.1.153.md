# 1.1.153 — 확대 capture blend의 16x 한정 GPU 이식

2026-09-21. 기준 1.1.152 HEAD 1b13260b. 메인 checkout과 빌드는 F:/melonDS, build/windows-dev다.

## 구현 — 행당 한 번의 deferred dispatch

확대 mode>=2 capture blend(A=장치 상주 rendered image, B=host 업로드)가 적격 행에서 GPU compute로 실행된다. 새 CaptureBlend.comp는 native 행 하나의 모든 확대 subrow를 한 dispatch로 처리하고, A는 RenderedImage를 imageLoad해 공개된 CPU 변환((p>>2)&0x3F3F3F|(p>>3)&0x1F000000 후 5비트 추출, alpha (a>>3)!=0)과 비트 단위로 같은 정수식을 쓰며 RenderXPos scroll wrap도 GetScaledLine과 동일하다. B는 행의 소스 구간을 host-visible Upload 버퍼에 memcpy한다(확대 captured 행 또는 native/FIFO 256-word 행). 결과는 host-visible Landing 버퍼에서 기존 CaptureRow staging으로 복사되고, 기존 staging copy·valid[line] publication·native VRAM 기록·fallback·계측 계약은 불변이다.

Device::SubmitAndWait를 Submit+WaitForSubmission으로 분리해 dispatch를 native capture CPU 작업과 겹치게 했다(deferred fence). 적격 조건: scale==16, mode>=2, control bit24(순수 3D A), full-width capture, RenderedScale==DisplayScale, 유효한 현재 RenderedImage, 정상 프레임. 생성·제출·대기 실패는 이 renderer 인스턴스에서 GPU 경로를 영구 비활성화하고, 행 중간 실패는 publication 전에 CPU 경로로 행을 재계산한다.

배율 제한은 측정 근거다: 행당 submit+wait의 고정 host 비용(~57us×192≈11ms/프레임)이 16x 미만에서는 CPU blend 비용을 넘어선다. 무제한 변형은 blend-FIFO 5x에서 +331% total 회귀(6/6 쌍)를 보였고, scale<16 early-return이 GPU 경로를 측정된 승리 구간에 한정한다.

## 남은 범위·한계

- 측정값은 생성 fixture의 RunFrame/host stage 시간이다 — 실게임 FPS·Qt 표시 지연이 아니다.
- 행 묶음 제출(다수 행을 한 submission에)은 Device의 명령 버퍼/fence 구조 변경이 필요해 이 단위 밖이다 — 성공하면 16x 미만도 후속 후보다.
- 실기·DSi·다른 OS/GPU·대화형 UI·장기 실행은 미검증이다.
