# 1.1.05 — ROM 교체와 종료 시 저장 데이터 보호

상태: 구현·Windows 빌드·로컬 회귀·배포 디렉터리 검증 확인(2026-09-10). 기준 소스: 1.1.04. 책임 버전과 실제 배포 증분은 구분하며, 이번 변경은 FS-03/06과 FS-02의 카트 저장 파일 읽기 경계다.

## 이번 증분의 5페이즈

1. **반례:** 잘못된 DS/GBA ROM, 새 저장 경로 쓰기 거부, 콘솔 준비 실패로 기존 카트·저장 관리자가 바뀌는 경로를 재현한다. 미발행 저장 요청·메모리 복사 후 pending·닫기 실패를 분리한다.
2. **교체 준비:** 현재 저장을 완료한 뒤 새 SRAM·카트·관리자를 준비한다. 준비 실패 시 기존 카트·경로·대기 카트를 유지하며, 콘솔 자원도 카트를 꺼내기 전에 읽는다.
3. **종료 복구:** 최신 버퍼를 원본에 쓰는 Flush와 별도 복구 사본 API를 연결한다. 닫힐 모든 인스턴스를 먼저 멈추고 재시도·취소·복구 사본 저장을 선택할 수 있게 한다. 어떤 자식 인스턴스가 취소해도 창 파괴 전에 전체 닫기를 취소한다.
4. **검증:** 실제 코어·카트·저장 관리자와 합성 자원, Qt 임시 파일·대화상자, 메시지 정책을 검사한다. Windows frontend 빌드와 최종 회귀를 기록한다.
5. **배포:** 같은 커밋의 실행 파일·소스·공개 계획을 묶는다. 기존 사용자 저장·설정·실행 환경을 보존하고 실제 게임·물리 저장장치 수락을 별도 기록한다.

## 동작과 보존 계약

현재 게임의 저장이 실패하면 교체나 reset을 중단한다. 사용자는 재시도하거나 창을 닫는 과정에서 복구 사본을 선택할 수 있다. 새 게임의 경로·SRAM·카트가 잘못되었을 때 기존 게임의 이후 저장 요청은 기존 관리자로 간다. 같은 게임을 다시 열 때는 먼저 최신 pending을 기록하고 그 파일을 읽는다.

BIOS·firmware 준비 실패는 활성/대기 카트를 꺼내기 전에 반환한다. 콘솔을 새로 만들어야 하면 먼저 생성한 뒤 교체한다. reset 실패는 메시지로 전달하고 복원 실패에 따른 기존 실행 차단을 해제하지 않는다. boot/reset/stop의 코어 변경 전에는 오디오·마이크 callback을 중지한다.

메모리로 복사한 저장 데이터는 원본 파일의 commit으로 간주하지 않는다. 복구 사본은 원본 경로와 pending을 바꾸지 않으며, 취소 후에도 원본 저장을 다시 시도할 수 있다. 동일한 정규화 경로를 복구 대상으로 지정해 원본 저장을 우회하지 않는다.

닫기 전에는 닫힐 인스턴스 전체를 일시 정지한다. 저장 실패에서 취소하면 이번 닫기가 추가한 pause만 해제한다. 복구 사본이 성공했을 때만 해당 실패를 보존한 상태로 닫기를 허용한다. 별도 화면만 닫고 인스턴스가 남는 경우에는 이 종료 절차를 실행하지 않는다.

## 검증 기록

수정 전 ROM/콘솔 실패 6종과 inactive GBA 저장 연결 1종이 실패했고 정상 DS/GBA 교체는 통과했다. 미발행 pending·메모리 복사 후 재시도 2종도 실패했다. 기존 closeEvent는 DS/GBA/firmware 저장 실패와 자식 인스턴스 취소 4종에서 창을 닫았으며 정상 닫기·보조 창 대조는 통과했다.

Windows x64 Release frontend 빌드와 최종 CTest **110/110, skip 0, 16.98초**를 확인했다. GCC 16.2.0, CMake 4.4.3, Qt 6.11.2, SDL 2.32.10, Zstd 1.5.7 구성에서 C23/C++26·JIT·OpenGL·선택 AVX2/AVX-512 커널을 빌드하고 LTO는 기존 예외에 따라 비활성화했다. 기존 Qt/toml11 경고는 남아 있다.

변경 경계의 검사는 카트 교체·SRAM 20종, 종료 UI 10종, 저장 관리자 13종과 상태 메시지 검사다. 전체 회귀에는 기존 interpreter·warmed JIT·fastmem 복원과 실제 OpenGL/Compute의 합성 출력 검사도 포함한다. 종료 fixture의 moc가 생성된 함수 include를 먼저 읽도록 CMake 의존성을 명시했고 후속 증분 빌드의 의존성 순환도 해소했다.

증분 빌드 확인에서 갱신된 moc에 대한 종료 fixture 재컴파일이 남아 있어 해당 target만 재빌드했다. 종료 10/10을 다시 확인한 뒤 추가 빌드 작업이 없음을 확인했다. 전체 회귀는 반복하지 않았다.

배포 디렉터리의 EXE/DLL 129개에서 누락된 import가 없으며, 개발 도구가 없는 PATH에서 `--help` 종료 0과 Usage 출력을 확인했다. 공개 계획 14개의 로컬 파일 링크와 개인 경로 검사도 통과했다. 패키지 영수증은 생성 시 소스 커밋·EXE/ZIP SHA-256·ZIP 무결성·비공개 파일 제외 결과를 기록한다.

## 수락 한계

- CartReplacement는 실제 코어·카트 parser·저장 관리자에 생성한 ROM 자원과 임시 파일을 공급한다. 게임 타이틀의 장기 진행·실기 대조는 아니다.
- FrontendClose는 실제 Qt close event·대화상자·파일 선택을 실행하며 EmuInstance/EmuThread/SaveManager는 계약 대역이다. 실제 저장 관리자 검사는 SaveManagerIO와 CartReplacement가 담당한다. 실제 frontend thread·물리 장치와 결합한 종료 수락은 남아 있다.
- 복구 사본이 존재해도 원본 저장 성공으로 표시하지 않는다. 읽기 전 reset이 남은 save import, 같은 basename 충돌, RTC 등 다른 저장 경계까지 해결됐다는 뜻이 아니다.
- 저장 상태·SRAM 형식과 기존 저장 이름을 바꾸지 않는다. 이전 실행 파일로 복귀할 수 있다. 성능 향상 수치는 주장하지 않는다.
