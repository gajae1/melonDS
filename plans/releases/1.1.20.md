# 1.1.20 — 캡처 보존·GL 자원 수명

상태: Windows 구현·로컬 회귀와 게임 대조 확인. 기준 1.1.19, 검증일 2026-09-10. GR-01/04/06의 실제 증분이며 책임 버전 1.1.20의 DSi NDMA/clock 과제 완료를 뜻하지 않는다.

## 5페이즈

1. **재현:** GPU에만 남은 캡처와 CPU가 읽은 캡처를 나눠 배율 변경·다음 소비자의 값을 확인한다. GL 객체는 정상 생성/파괴와 첫 shader 실패에서 실제 생존을 검사한다.
2. **최소 수정:** 이전 크기에서 캡처를 VRAM에 보존한 뒤 재할당한다. 확인된 소유 객체 해제 누락·미초기화 ID를 수정한다.
3. **통합:** 같은 backend 설정·renderer 교체·source A/B/혼합 캡처·CPU 읽기·후속 texture 재사용을 기존 경로에 연결한다. 중간 캡처의 시각 모델과 전체 RAII 구조는 별도 범위다.
4. **검증:** 실제 두 GL backend와 software의 생성 입력, CPU 소비자, 살아 있는 context에서의 자원 해제, 전체 Windows 검사와 같은 게임의 이전 프레임을 확인한다.
5. **배포:** 확인한 범위를 Windows 실행 파일·소스·공개 계획에 반영하고 개인 입력은 제외한다. 다른 driver/OS·native A64·실기·장기 플레이 조건을 유지한다.

## 배율 변경의 캡처 보존

같은 GL renderer에서 배율을 바꾸면 `CaptureOutput128/256`을 새 크기로 재할당하면서 이전 캡처 픽셀을 잃었다. [Khronos glTexImage3D](https://raw.githubusercontent.com/KhronosGroup/OpenGL-Refpages/main/gl4/glTexImage3D.xml)는 null 데이터로 할당한 영역의 이미지 내용을 보장하지 않는다. 실제 두 GL backend에서 배율 변경 후 guest CPU가 읽은 값은 0이었고, CPU가 먼저 읽어 VRAM을 보존했어도 후속 3D texture가 이전 GPU 참조를 사용해 잘못된 색을 만들었다.

이전 배율에서 기존 `SyncAllVRAMCaptures`를 실행하고 나서 크기·저장 영역을 변경한다. 이미 CPU가 읽은 캡처는 다시 GPU에서 읽지 않고 해당 참조만 폐기한다. 같은 배율이나 최초 크기 설정에는 추가 동기화를 넣지 않는다. 이 보존 경계는 설정 변경 시 필요하며 매 프레임에 새 readback을 추가하지 않는다.

`GLCaptureReadback`은 실제 3D 삼각형·배경을 source A로, VRAM을 source B로 사용한다. source A/B와 A+B, 128×128·256×64/128/192, 목적지 bank 끝의 순환을 검사한다. [GBATEK 캡처 계약](https://problemkaputt.de/gbatek.htm#dsvideocaptureandmainmemorydisplaymode)의 크기·source·offset·15-bit 출력과 정수 합의 기대값을 사용한다.

각 backend의 5개 입력을 1x/2x와 무변경·미동기화 상태에서 변경·CPU가 읽은 뒤 변경으로 나눠 30조건을 실행한다. 생성 ARM9 LDRH가 실제 메모리 경로로 캡처를 읽고 결과를 guest RAM에 기록한다. 128/256 입력은 캡처를 direct-color 3D texture로 다시 사용하고 다른 bank에 재캡처한 뒤 CPU로 읽는다. fixture는 캡처 전에 임의의 GL barrier/finish/readback을 추가하지 않는다.

수정 전 software 30조건과 두 GL backend의 무변경 대조는 통과했다. 각 GL backend의 미동기화 배율 변경 10조건은 CPU probe 5개 모두 틀렸고, 재사용 대상 128/256 texture는 CPU가 미리 읽었더라도 실패했다. 수정 후 두 GL backend의 60조건 모두 통과한다.

중간 색 강도를 반복 캡처/텍스처화할 때 기존 GL과 software 사이 1단계 차이도 관찰했다. 이번 회귀는 주색 끝값과 정수 합으로 배율 보존을 분리했으며 전체 색 정밀도·반올림·실기 동등성을 주장하지 않는다. 해당 차이는 GR-08의 별도 oracle 비교로 남긴다. DMA·진행 중 캡처·source A의 모든 2D 레이어·모든 offset 조합도 이번 검사의 범위 밖이다.

## GL 자원 수명

classic GL renderer를 같은 context에서 두 번 생성·파괴하자 매번 clear/final-pass program 4개와 index buffer 1개가 남았다. 해당 소유 객체의 해제를 추가했다. texture cache의 정상 상주 정책이나 공유 객체 소유권은 변경하지 않는다.

첫 shader compile이 실패하면 GL 공통/2D renderer의 미초기화 handle과 classic 3D의 `ClearBitmapTex`를 destructor가 삭제 대상으로 사용했다. 소유 handle을 0으로 초기화하고, 실패한 vertex/fragment program을 삭제한 뒤 결과 ID도 0으로 비운다. 2D B가 A와 공유하는 shader·mosaic의 해제 책임은 기존 A에 유지한다.

`GLResourceLifetime`은 실제 driver의 생성·삭제에 위임하면서 program/buffer/texture를 기록한다. context가 살아 있는 상태에서 소유자 파괴 후 실제 생존과 미삭제 이름을 확인한다. 아직 bind하지 않은 생성 buffer는 `glIsBuffer`만으로 판정할 수 없어 이름별 삭제 기록을 함께 사용한다. 사용 중 program의 지연 삭제도 참조를 해제한 뒤 판정한다. [Khronos glIsBuffer](https://raw.githubusercontent.com/KhronosGroup/OpenGL-Refpages/main/gl4/glIsBuffer.xml), [glDeleteProgram](https://raw.githubusercontent.com/KhronosGroup/OpenGL-Refpages/main/gl4/glDeleteProgram.xml).

실패 case는 첫 shader source를 실제 compile 오류로 바꾸며 정상 shader 오류 반환을 관찰한다. 재사용 raw storage에 무관한 texture 이름을 남긴 뒤 정상 생성자를 실행하여 초기값 공백을 드러낸다. 생성된 객체의 member를 나중에 덮어쓰지 않는다. 수정 전 두 실패 경로에서 대조 texture가 삭제됐고, 수정 후 정상 2회·공통 실패·3D 실패 모두 소유 객체 잔존/미삭제 0, 무관한 객체 삭제 0, GL 오류 0이다. 공통 초기화 실패에서는 실제 software fallback도 확인한다. 별도 3D child 실패를 전체 프런트엔드 복구로 해석하지 않는다.

실패 전 미초기화 읽기는 C++의 정의되지 않은 동작이므로 원 결함이 모든 compiler에서 같은 ID 삭제로 나타난다고 주장하지 않는다. 이 검사는 현재 context에서의 객체 수명이며 surface/context 상실·전체 Qt 종료·다른 driver 수락은 별도다.

## 통합 검증

- Windows x64 Release, GCC 16.2, Qt 6.11.2, SDL 2.32.10, C23/C++26. JIT·OpenGL/Compute와 기존 runtime ISA dispatch 구성의 전체 frontend 빌드 성공.
- 전체 CTest **403/403, skip 0**, 20.42초. source A/B·혼합·wrap·배율과 후속 소비자 90조건, 현재 context의 자원 수명 3개 case를 포함한다.
- 두 비공개 DS 게임을 fastmem으로 software/OpenGL/Compute 각각 3,600프레임 실행했다. 6개 최종 프레임 모두 같은 게임·입력·renderer의 기존 1.1.19 결과와 바이트가 일치한다. 화면도 정상 도입부인지 확인했다. 이전부터 있던 renderer/CPU 모드 간 차이의 전체 해결이나 장기 플레이 검증은 아니다.
- 배율 변경 경계에서 필요한 데이터 보존과 실제 객체 해제를 검증했다. 전체 FPS·비동기 readback 속도·입력/오디오 지연 개선 수치는 측정하지 않았으며 오디오 설정·보간 옵션은 변경하지 않는다.

실행 파일은 `1.1.20-melonDS.exe`, 배포 ZIP은 `1.1.20-melonDS-windows-x64.zip`과 `1.1.20-melonDS-source.zip`이다. 실행 파일·필요 DLL/plugin·라이선스만 선별하며 게임·설정·저장 데이터를 포함하지 않는다.
