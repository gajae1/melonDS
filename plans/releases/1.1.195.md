# 1.1.195 — Vulkan GPU2D 저장소 재사용과 추가분 전송

2026-09-28. 릴리스 소스 커밋은 1514738319c362a2113f53b3e3adadabef7f8557다. SDL3·SDL2 패키지와 플랫폼 CI 검증을 완료했다.

## 구현

기존 GPU2D는 제출마다 CPU 스냅샷 저장소와 뷰를 다시 만들고 전체 입력을 GPU에 복사했다. 이제 변경하지 않는 앞부분을 CPU/GPU 양쪽에 보존하고, 새 페이지·테이블·병합 명령 및 현재 레코드만 쓴다. 화면 중간 변경은 새 불변 페이지로 기록하므로 프레임 시작 RAM 하나로 대체하지 않는다.

입력 버퍼가 커질 때는 기존 GPU 값도 GPU 내부 복사로 옮긴다. CPU에 남은 부분 기준값으로 GPU 캡처·OR 병합 결과를 덮어쓰지 않는다. 복사 원본 버퍼는 fence 완료까지 유지한다. 매핑 장치 메모리·업로드 장치 메모리·호스트 대체 경로 모두 같은 계약을 따른다.

16MiB CPU arena의 여유가 2MiB 미만이 되면 기존 압축 경로로 새 세대를 시작한다. 소비한 OBJ는 영구 이력 슬롯을 가리키고, 아직 소비하지 않은 prefetch는 GPU 원본 참조를 다음 압축까지 보존한다. 입력 세대 0은 기존 전체 업로드 API다. 기존 선택형 진단의 upload-copy 계수에는 실제 CPU 입력 쓰기를 포함했다.

캡처가 있는 묶음의 동기 완료와 CPU 상태 스냅샷은 유지한다. 전체 물리 VRAM을 CPU 처리 없이 에뮬레이션하는 구현이 아니다. 새 ISA 요구나 게임 이름별 특례는 추가하지 않았다.

같은 후보 소스의 **GPU2D 대 CPU2D**를 4배율에서 직접 비교한 한 쌍씩의 결과는 다음과 같다.

## 정확성·배포

- 두 GPU·두 게임·1/4배율의 8조건에서 누적 framebuffer digest·최종 PPM·누적 PCM이 1.1.194와 모두 같다. 추가 반복 쌍과 네 CPU2D 직접 비교도 exact다.
- 기존 native2D event/batch/캡처 overlap·OBJ/texture/hires OBJ·scale/backend toggle 검사를 통과했다. 비활성 OBJ 재매핑과 pending readback·정지·리셋·배율 변경·소멸도 확인했다.
- 두 GPU의 세 메모리 경로에서 실제 GPU copy/OR 결과를 바이트로 readback했다. 같은 세대 재사용과 버퍼 확장 뒤에는 GPU 값이 유지되고 새 세대에서는 새 CPU 기준값으로 바뀐다. 강제 경로 선택은 실제 메모리 부족 재현을 뜻하지 않는다.
- GPU 캡처를 참조하는 fresh OBJ prefetch를 제출 후 보존한 뒤 arena를 용량 한계까지 채웠다. CPU가 VRAM을 수정하고 다음 실제 scanline에서 압축해도 먼저 읽은 sprite가 독립 SoftRenderer와 같았다. CPU 접근 전의 prefetch 유지가 GPU 값을 guest RAM으로 강제 다운로드하지 않았고 CPU2D fallback도 실행하지 않았다.
