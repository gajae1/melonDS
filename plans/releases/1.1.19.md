# 1.1.19 — 캡처 텍스처 설정·렌더러 실패·장치 이벤트

상태: Windows 구현·로컬 회귀와 게임 대조 확인. 기준 1.1.18, 검증일 2026-09-10. GR-02/03·CJ-08의 실제 증분이며 기존 책임 버전 1.1.19의 DSi SD/MMC 과제 완료를 뜻하지 않는다.

## 5페이즈

1. **근거·재현:** 같은 캡처의 clamp/repeat/mirror variant를 실제 GPU에 보낸다. 셰이더 실패가 완료로 처리되는 경계와 코어 IRQ/DMA/sleep 중 한 장치 경계를 정상 입력과 대조한다.
2. **최소 수정:** 캡처 종류에서 매 variant의 texture unit을 결정한다. 재현된 셰이더/장치 오류만 수정하고 추정한 타이밍이나 기본 설정을 바꾸지 않는다.
3. **통합:** 일반 texture와 캡처 사이 전환, 유효 renderer 소유권과 실패 전달, CPU별 시각 단위를 보존한다. 공유 renderer/frontend 파일은 한 작성자가 통합한다.
4. **검증:** 실제 캡처·sampler 상태·픽셀, 실패 주입·복구, 생성 코어 장치 회귀를 실행한다. 전체 Windows 검사와 같은 게임 입력의 이전 renderer/core를 대조한다.
5. **배포:** 확인된 범위를 Windows 실행 파일·소스·공개 계획에 반영한다. 다른 드라이버·native A64·실기 타이밍·장기 플레이를 별도 수락으로 남긴다.

## 캡처 sampler

Compute의 raster variant는 캡처 종류에 따라 texture unit 1 또는 2를 사용한다. 기존 코드는 texture가 바뀔 때만 unit을 결정하고, 같은 캡처에서 sampler만 바뀌면 0으로 초기화된 unit에 새 sampler를 연결했다. 이 때문에 연속된 repeat/mirror 도형이 앞선 clamp 설정으로 그려졌다.

현재 variant의 texture 종류로 unit을 매번 결정한다. texture 변경 시의 binding 생략은 유지하며 일반 texture와 캡처 사이를 이동하면 sampler를 해당 unit에 다시 연결한다. shader·batching·texture cache 자체를 교체하지 않는다. [OpenGL 4.3 core §8.2](https://registry.khronos.org/OpenGL/specs/gl/glspec43.core.pdf)의 sampler 상태는 연결한 texture unit에 적용되므로, 같은 texture를 재사용한다는 이유로 다른 unit의 sampler를 변경할 수 없다.

기존 `GLFrameReadback`에 source B의 실제 VRAM 캡처를 추가했다. 128×128·256×192 캡처를 texture로 매핑하고 가로·세로 방향별 clamp/repeat/mirror, 일반 texture, 캡처 복귀의 5개 도형을 그린다. 텍스처 경계나 256 캡처의 미기록 아래쪽 영역을 피한 좌표를 사용한다. 새 shader나 임의로 주입한 capture texture로 생산 경로를 대체하지 않는다.

수정 전 네 조건 모두 sampler 상태 2개와 검사한 내부 픽셀 125개 중 50개가 실패했다. 수정 후 네 조건 모두 오류 0이며 기존 32개 frame sampling/barrier, 1x·2x 좌표 전환과 framebuffer 해제 검사도 통과한다. 실제 driver에 보낼 직전 상태를 관찰하지만 sampler binding을 고치지 않으며 출력 뒤 readback용 barrier만 사용한다. 이 검사는 S/T wrap의 선정한 좌표와 native GPU 소비자까지의 증거이고 비표준 캡처 높이·offset wrap·모든 도형·DS 실기 결과를 포괄하지 않는다.

## Compute 실패와 복구

기존 코드는 실제 source compile 또는 program link가 실패해도 33개 단계 완료와 render 진입을 허용했다. 실패 주입 시 나머지 shader를 계속 만들고 무효 dispatch를 3회 시도했다. compile 실패에는 이미 삭제한 shader를 다시 삭제하는 GL 오류도 있었다. Compute에 필요한 4.3 capability가 아닌데도 초기화가 성공하는 판정 경계도 재현했다.

초기화에서 실제 GL version과 필수 compute 함수 포인터를 확인한다. 첫 shader 실패를 bool 결과와 terminal 상태로 전달하고 이후 compile/dispatch를 중단한다. program ID를 0으로 초기화하고 삭제 후 비우며 부분 컴파일·정상 종료 모두 해제한다. compile 실패의 shader와 link 실패의 program도 삭제 후 ID를 비운다. [Khronos glDispatchCompute](https://raw.githubusercontent.com/KhronosGroup/OpenGL-Refpages/main/gl4/glDispatchCompute.xml)의 core 4.3·유효 compute stage 계약을 따른다.

프런트엔드는 같은 호출에서 기존 `updateRenderer`로 실제 SoftRenderer를 생성하고 세션 renderer 상태를 맞춘 뒤 오류를 안내한다. null을 무시하는 NDS의 wrapper에 기대지 않으며 교체한 이전 renderer 참조를 다시 읽지 않는다. 초기화 실패도 실제 활성 renderer에 맞춰 기록한다. 저장된 사용자 선호는 유지하며 명시적 재선택으로 다시 시도할 수 있다. 컴파일 시간 제한에서 초기화되지 않은 member를 읽던 부분은 해당 함수의 유효한 SDL counter 변환으로 바꿨다.

`GLFrameReadback compute-failure`의 6개 case는 정상, capability 판정, 실제 driver compile/link 실패, 배율 변경 뒤 재컴파일, 실제 프런트엔드 메서드의 복구를 검사한다. 수정 후 실패 case의 무효 dispatch 시도는 0이고 첫 실패에서 source compile을 멈춘다. 1x→2x 재컴파일은 기존 정상 33개와 실패한 새 1개까지만 실행한다. GL 오류 없이 정리되고 실제 software 코어가 프레임을 진행해 RAM framebuffers를 반환한다.

프런트엔드 case는 현재 소스에서 추출한 `updateRenderer`·`compileShaders`와 실제 GPU를 사용해 오류 통지 1회, 정상 재선택, 재컴파일 실패, capability 거부 후 반복 update를 확인한다. 설정 읽기·OSD 전달은 격리했으므로 Qt 전체 event loop·실제 화면의 안내 표시 수락을 대신하지 않는다. capability는 실제 4.3 context의 version 조회를 3.2로 주입한 판정 검사이며 실제 3.2-only 장치 검증이 아니다. 실패 fixture의 dispatch는 호출을 계수한 뒤 driver 전달을 막고, 정상 픽셀 출력은 별도의 실제 GPU capture 검사로 확인한다.

현재 binary shader cache 복원·저장은 실행 코드에서 비활성이다. 이번 source 재컴파일을 cache-hit 검증으로 기록하지 않으며, 재활성화 때 binary 거부→source 성공/실패를 별도로 검증한다.

## 타이머·HALT·IRQ

생성 ARM9 guest가 실제 MMIO로 Timer0를 시작하고 HALT한 뒤 overflow IRQ로 깨는 경로에서, IRQ 진입이 기존 CPSR.F를 무조건 1로 바꾸는 오류를 재현했다. [ARM DDI 0100I A2.6.8](https://documentation-service.arm.com/static/5f8dacc8f86e16515cdb865a)에 따라 F를 보존하면서 I=1, T=0, IRQ mode로 전환한다. LR/SPSR·나머지 flags와 scheduler 시각 단위는 유지한다. DS timer/IME/IE/HALT 계약은 [GBATEK](https://problemkaputt.de/gbatek.htm#dstimers)를 함께 대조한다.

`CoreExecution device-execution`의 F=1 정상 대조, warmed F=0 IRQ, IME 차단, IE 차단, CPSR.I 차단 후 IRQ 진입 없는 wake의 다섯 조건을 interpreter/JIT/fastmem으로 실행했다. 수정 전 F=0 조건만 실패했고 수정 후 15개 조건 모두 통과한다. guest IRQ handler의 상태 읽기·진입 횟수·LR/SPSR·wake 뒤 명령 실행과 Timer0 첫 overflow보다 이른 handler 진입이 없음을 확인한다. 이는 ARM9의 선정한 상대 경계이며 ARM7/Thumb·IRQ return/nesting·DMA/GX/sleep 동시점·실기 절대 latency 수락은 남긴다.

## 통합 검증

- Windows x64 Release, GCC 16.2, Qt 6.11.2, SDL 2.32.10, C23/C++26. JIT·OpenGL/Compute와 기존 runtime ISA dispatch 구성의 전체 frontend 빌드 성공.
- 전체 CTest **397/397, skip 0**, 13.86초. 새 반례를 먼저 실패시키고 최소 수정 후 확인한 결과를 포함한다.
- 두 비공개 DS 게임에서 같은 입력으로 3,600프레임씩 현재 software interpreter/JIT/fastmem 6회, OpenGL/Compute 4회를 실행했다. 기존 1.1.18 software 결과를 재사용하고 GL 두 backend는 변경 전 baseline 4회를 별도 보존했다. 현재 10개 최종 프레임 모두 같은 게임·실행 모드·renderer의 이전 결과와 digest 및 바이트가 일치한다. GL 화면은 게임의 정상 도입부인지도 확인했다.
- 이전부터 있던 interpreter/JIT 또는 renderer 간 화면 차이를 모두 해결했다는 뜻은 아니다. 평균 FPS·물리 입력/오디오 지연 개선 수치는 측정하지 않았다. 이번 버전은 새로운 보간 옵션이나 기본 설정 변경을 포함하지 않는다.

실행 파일은 `1.1.19-melonDS.exe`, 배포 ZIP은 `1.1.19-melonDS-windows-x64.zip`과 `1.1.19-melonDS-source.zip`이다. 실행 파일·필요 DLL/plugin·라이선스만 선별하며 게임·설정·저장 데이터를 포함하지 않는다.
