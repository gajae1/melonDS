# 1.1.165 — 저장 상태 복원 후 3D 프레임 재구성

2026-09-23. Windows UCRT64 Release. 이전 버전 1.1.164.

저장 상태를 불러오면 게스트의 3D 폴리곤 상태는 복원되지만 호스트 렌더러의 색·깊이 버퍼는 저장되지 않았다. 다음 화면 라인이 이전에 준비된 3D 프레임을 캡처하면 빈 버퍼가 VRAM에 쓰일 수 있었다. 성공한 전체 상태 로드의 마지막에 복원된 폴리곤 상태로 그 프레임을 다시 렌더한다. 저장 경로와 상태 파일 형식은 바꾸지 않았다.

기존 `SoftwareThread` 실제 코어·렌더러 사례에 로드 전에 렌더러 영상만 빨강으로 바꾸고, 저장된 초록 영상이 로드 직후 다시 보이는 검사를 추가했다. 복원 호출을 제거한 상태에서 `(0,0)`이 빨강으로 남아 실패했고, 복원 호출을 되돌린 뒤 관련 6개 사례가 통과했다. 사설 Solatorobo 상태 실험에서는 인터프리터로 저장한 6,000프레임 상태를 로드한 뒤 첫 프레임의 전체 상태가 연속 실행과 바이트 단위로 같았다. 이 수정이 적용된 개발 빌드에서 이어 실행한 6,000프레임의 최종 PPM도 같은 빌드의 12,000프레임 연속 실행과 일치했다. ROM·두 원본 save·입력 스크립트는 해시와 수정 시각이 유지됐다. 원시 기록은 `local-docs/bv17-state-resume-20260923/`에 있다.

별도 JIT 실험에서는 저장 직후 상태를 불러오지 않고 `JIT.Reset()`만 실행해도 로드 후의 ARM9·CP15·RAM·3D 상태 차이가 그대로 재현됐다. 이는 JIT 캐시 이력 문제를 좁힌 증거이며 이번 3D 복원 수정으로 해결했다고 주장하지 않는다. 호스트 PCM 출력 큐는 저장 상태에 포함되지 않으므로 PCM 파일의 바이트 단위 연속성도 이번 결과로 수락하지 않는다. Qt 화면의 실제 픽셀·오디오 장치·물리 장치·전체 게임 수명은 별도 수락 대상이다. JIT 원시 기록은 `local-docs/bv17-jit-reset-20260923/`에 있다.

독립 소스 `build/1.1.165-source`의 Release 빌드는 exit 0, 전체 CTest는 **1,022/1,022** 통과했다(165.11초). 제품 커밋 `8dde7025`의 소스 식별자 `08de5eb921ee55d45fda70d745c7774e6c63218af77b83252c8f808b4719d34b`가 배포 실행 파일의 내장 식별자와 일치한다. 기존 작업 중인 `src/teakra/src/test_generator.cpp`는 커밋·빌드·패키지에 넣지 않았다.

Windows 배포와 패키징은 각각 exit 0이었다. 런타임 ZIP은 325개 파일·106,732,040바이트, 소스 ZIP은 18,466,252바이트다. 제한된 PATH의 `--help`는 exit 0, ZIP에 알려진 개인 파일은 0개다. 배포는 설치된 19개 의존 패키지의 버전·라이선스 파일 해시가 적힌 기존 보충 목록을 사용했다. 첫 시도는 이 인자를 빠뜨려 중단됐고, 빈 부분 디렉터리를 별도 보존한 뒤 새 대상에 다시 배포했다. Qt 번역 catalog와 선택적 D3D12 구성요소 부재 경고가 남아 있으므로 번역 UI와 D3D12 동작은 수락하지 않는다.
