# 1.1.131 — 캐시 비우기·증가 감시와 Vulkan 업로드 묶음

2026-09-16. 기준 소스는 1.1.130 `012bc4e2`. GR-14/15·BV-07의 제한된 후속 구현이다.
Vulkan 1~16배 지원, native 캡처, guest 타이밍과 SPU 계산은 유지한다. 전체 계획 완료나 실기 정확성 인증은 아니다.

## 캐시 정책과 클리어

Vulkan pipeline cache는 원래부터 VkDevice 소유 RAM 객체였으며 디스크 저장 기능은 없었다.
Video settings에 **Clear Vulkan pipeline cache**를 추가했다. 기존 메시지 큐로 에뮬레이션 스레드에서 처리하며,
완료 전 중복 요청을 막고 renderer가 없으면 실패 상태를 표시한다. 현재 pipeline·텍스처·프레임·guest capture를 파괴하지 않는다.
32개 pipeline 생성 뒤 캐시 데이터 크기를 조회하고 32MiB 초과 시 자동으로 비운다.
이것은 export 가능한 데이터 크기의 소프트 제한이다. 드라이버 실제 상주 메모리나 transient peak의 하드 상한이 아니다.
캐시 객체를 비워도 기존 pipeline은 유효하며 다음 생성 시 캐시를 새로 준비한다.
드라이버 전역 디스크 캐시나 다른 앱 파일은 삭제하지 않는다. 자세한 구분은 [캐시 정책](../Caching.md)을 따른다.
OpenGL의 호출되지 않던 옛 shadercache 입출력과 주석 처리된 binary 경로를 제거했다. 기존 사용자 파일을 삭제한 것은 아니다.

## 전송 최적화

UploadClearBitmap의 색·깊이 이미지를 한 staging 버퍼의 서로 다른 offset에 준비해 하나의 command submission/fence로 전송한다.
단일 이미지 업로드와 barrier/record 코드를 공유한다. GPU 완료를 기다린 뒤 반환하며 guest 소비 시점을 뒤로 미루지 않는다.
입력 검증 및 staging 확보는 기록 시작 전에 수행한다. 성장 실패·잘못된 입력은 이전 이미지를 그대로 남기고 부분 제출을 하지 않는다.
최대 staging이 기존 clear 한 장의 256KiB에서 두 장의 512KiB로 커져 pipeline 수명 동안 유지되는 비용이 있다.
실제 queue 제출은 2→1이며, shader 수식이나 이미지 형식은 바꾸지 않았다.

## 합성 측정

동일 GCC16.2/C++26/-O3/-fwrapv와 RTX5080에서 baseline 소스와 수정된 pipeline을 비교했다.
각 실행은 8회 준비 뒤 100회 clear-bitmap 업로드의 평균을 측정한다.
순서를 무작위로 바꾼 준비 1쌍과 측정 7쌍, 총 16개 실행을 같은 논리 CPU에 고정했다.
측정 중 다른 자체 빌드/GPU 테스트는 실행하지 않았고 모든 짝의 최종 전체 이미지 checksum이 일치했다.
중앙값은 **522,193ns → 307,475ns, 약41.12% 감소**했다.
렌더링 전체나 실제 게임 FPS가 아니라 두 이미지 동기 업로드 루틴의 비용이다. CPU 주파수와 사용자의 다른 프로그램은 통제하지 않았다.

## 검증 내용

캐시 제어 API가 없는 baseline에서 새 검사는 컴파일 단계에서 실패했다. 구현 뒤 실제 GPU에서
수동 clear/중복 clear/재생성/32MiB 경계/자동 clear/캐시 미사용의 출력 일치를 검사한다.
기존 UI에서는 버튼이 없어 실패했다. 구현 뒤 비활성 조건·중복 요청·완료/실패 표시·설정 보존을 검사한다.
현재 message dispatcher는 GL current 실패 조건에서도 cache 제어를 수락하고 완료 응답을 보내는지 fixture로 검사한다.
Vulkan renderer 검사는 1x/2x/3x, Z/W와 texture format별로 cache clear 직후 현재 프레임을 대조한다.
clear-pair RED는 실제 queue 제출2회로 실패했다. 수정 뒤 제출1회, 성장 실패/잘못된 입력/후속 staging 재사용과 전체 이미지가 일치한다.
GL/Vulkan 공유 graph의 여러 장면과 고배율 대조는 실기나 Classic 전역 정답을 대신하지 않는다.

## 남은 범위

native 실기 화면 차이, GPU 2D/capture·직접 GPU 표시, 모든 texture upload의 프레임 단위 묶음은 이번에 완성하지 않았다.
메모리 선택·pipeline cache·반복 전송의 이득을 실제 게임과 다른 GPU/OS에서도 비교해야 한다.
오디오 제품 소스·계수는 변경하지 않았다. 장기 청취/장치 탈착/물리 지연은 독립 수락 과제로 유지한다.
예전 빌드 산출물과 build/evidence는 개발 자료이며 자동 삭제하지 않는다. 앱 cache 정책과 별개다.
검증 원자료는 `build/evidence/cache-controls-1.1.131/`에 보존한다. Actions·개인 ROM/BIOS/NAND/저장 파일은 사용하지 않는다.

## 중단 후 재개 검증 — 2026-09-16

중단 때 남은 27개 변경 파일의 SHA-256을 보존하고 실제 코드·기존 실패 로그·정책 문서를 대조했다.
이번 재개에서 기존 전체 타깃의 증분 빌드와 전체 CTest를 다시 실행했다.
**962/962 통과, 실패0·skip0, 102.92초**이며 JUnit과 `resume-full-tests.log`에 남겼다.
이는 이 Windows 구성의 등록 테스트 전체다. 실기·다른 GPU/OS·모든 게임에 대한 인증은 아니다.
Vulkan cache 데이터 조회는 실제 소스에서 `pData=nullptr` 한 경로만 남아 있고, 앱의 shadercache 파일 입출력 참조는 없다.
드라이버의 별도 디스크 캐시, 과거 빌드가 남긴 파일과 개발 산출물은 삭제하지 않았다.

업로드 비교 실행 파일도 기준 HEAD의 ComputePipeline 소스와 현재 소스로 다시 빌드했다.
다른 자체 GPU 검사·빌드가 없는 상태에서 같은 논리 CPU에 고정해 준비1쌍과 측정7쌍을 재실행했다.
새 중앙값은 **213,699ns → 126,800ns, 40.66% 감소**이며 모든 짝의 전체 이미지 checksum이 일치했다.
위의 이전 측정과 절대 시간은 달라 별도 기록으로 보존한다. 주파수와 사용자 프로그램까지 통제한 결과는 아니다.
기존 측정 JSON은 `*-before-resume.json`, 새 값은 `paired-clear.json`과 `clear-benchmark-summary.json`에 있다.
메인 `F:/melonDS`로의 통합·빌드 여부는 후속 메인 경로 검증 기록을 따른다.
