# 1.1.17 — DTCM 빠른 메모리 매핑·이벤트 취소

상태: 구현·Windows 빌드·로컬 회귀 완료. 기준 1.1.16. CJ-05/CJ-07의 증분이며 기존 책임 버전 1.1.17의 Compute renderer 과제 완료를 뜻하지 않는다.

## 5페이즈

1. **근거·재현:** CP15 설정 변경과 실제 호스트 메모리 연결을 대조한다. 같은 시각의 앞선 callback이 뒤 이벤트를 취소하는 입력을 생산 scheduler에 실행한다.
2. **수정:** DTCM 자체와 다른 RAM의 DTCM 제외 구간을 구분하고, 이전 구간의 끝을 크기로 계산한다. callback 실행 직전에 현재 활성 비트를 확인한다.
3. **통합:** 작은 DTCM의 물리 bank offset·가상 범위를 보존하고, 호스트 페이지보다 작으면 기존 fallback을 사용한다. 이벤트 snapshot·순서·재예약 계약을 유지한다.
4. **검증:** warmed guest 읽기/쓰기, RAM mirror 복원·ARM7 유지·코드 보호, 4/8/16/32 KiB 설정과 주소 공간 끝을 검사한다. 전체 Windows CTest와 두 게임의 이전 코어 비교를 수행한다.
5. **배포:** 실행 파일·소스·공개 계획을 버전으로 묶고, 플랫폼·게임·타이밍의 미확인 범위를 명시한다.

## 원인과 변경

`MapAtAddress`와 `Mapping::Unmap`은 DTCM을 다른 메모리 안의 제외 구간처럼 처리했다. 실제 DTCM region에도 같은 조건을 적용해, 정상 16 KiB 설정에서 OS view를 만들지 않고 매핑 성공으로 기록했다. 두 메서드 모두 다른 메모리 region에만 DTCM 제외 조건을 적용한다. 게임의 읽기 결과는 fault 후 느린 helper로 전환해도 같을 수 있으므로 값 일치만으로 빠른 경로의 연결을 판정하지 않는다.

`RemapDTCM`은 이전 끝 주소에 크기 대신 mask를 더했다. DTCM을 서로 다른 RAM mirror로 옮기면 이전 RAM의 제외 구간이 남았다. 이전 크기로 끝을 계산하고 배타적 끝 주소를 64비트로 비교한다. 재연결되는 RAM의 코드 페이지 보호와 ARM7의 별도 view를 유지한다.

작은 4/8 KiB 설정은 16 KiB 물리 bank 전체를 연결하면 설정 밖 주소까지 노출된다. `GetMirrorLocation`이 실제 설정 크기와 물리 bank 내 offset을 사용하도록 보완했다. 호스트 페이지보다 작은 view는 연결하지 않고 기존 느린 접근을 사용한다. 큰 설정의 여러 가상 mirror는 기존 물리 bank를 공유한다.

`RunSystem`의 최초 snapshot에는 callback이 취소한 이벤트도 남았다. 실행 직전에 현재 활성 mask를 확인해 취소된 이벤트를 건너뛴다. 새로 생긴 slot은 다음 회차에 처리하고, 처음부터 활성인 slot의 같은 시각 교체는 현재 callback·인자로 실행한다. periodic 재예약은 이전 deadline 기준을 유지한다. 저장 형식이나 이벤트 세대 번호는 추가하지 않는다.

## 검증과 남는 범위

수정 전 16 KiB DTCM view는 매핑 성공 반환 뒤에도 Windows에서 예약 상태로 남아 읽을 수 없었다. 해당 조건을 고친 뒤에는 이전 RAM mirror가 이동 후에도 읽히는 두 번째 실패가 드러났다. 작은 DTCM 검사는 설정 밖 view가 읽히는 추가 실패를 검출했다. 각각의 수정 후 실제 view·값·해제와 guest 재진입이 통과한다.

호스트 관찰은 테스트 자신의 메모리만 [VirtualQuery](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtualquery)와 [ReadProcessMemory](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-readprocessmemory)로 확인한다. interpreter·일반 JIT·fastmem에서 실제 ARM9 프로그램을 두 번 실행하고, JIT는 두 번째 진입 전에 block 존재를 확인한다. 코드 페이지의 읽기 전용 보호·ARM7 RAM view 보존·32 KiB 설정의 물리 alias와 4 GiB 끝 해제를 포함한다.

실제 scheduler 6개 case 중 수정 전에는 `cancel-due`만 실패해 취소한 callback이 실행됐다. 수정 후 취소·미래 재예약·같은 시각 교체·periodic·신규 slot snapshot·정상 순서가 모두 통과한다.

최종 Windows x64 프런트엔드 빌드와 전체 CTest **385/385, skip 0, 병렬8에서 10.87초**를 확인했다. UCRT64 GCC 16.2.0·Qt 6.11.2·SDL 2.32.10, C23/C++26·Release·JIT·OpenGL/Compute 구성이다. 전체 검사에는 실제 OpenGL/Compute frame capture와 기존 입력 설정 회귀도 포함된다.

두 DS 게임에 같은 생성 입력·software renderer를 사용해 각 3600프레임씩 현재 interpreter/JIT/fastmem과 이전 1.1.16 interpreter/JIT를 비교했다. 총 10회가 종료 0·실행 상태 유지였고, 현재 JIT=fastmem=이전 JIT, 현재 interpreter=이전 interpreter였다. interpreter/JIT 사이의 기존 화면 차이는 그대로 남는다. 이 최종 프레임 비교를 전체 상태 동등성이나 장기 플레이 수락으로 확대하지 않는다.

이번 호스트 매핑 수락은 Windows x64의 4 KiB 페이지에서 얻었다. 다른 OS·native A64·16 KiB 호스트 페이지의 fallback 실행, MPU fault·DTCM resize/save-load의 전체 조합, IRQ/DMA/sleep의 장치 상호작용은 후속 범위다. 특정 게임에서 이 결함이 발생했다거나 FPS·입력 지연이 개선됐다는 측정 주장은 하지 않는다. 실제 DS/DSi 절대 타이밍·장기 게임 수락과 앞선 미완료 과제도 유지한다.
