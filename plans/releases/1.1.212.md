# 1.1.212 — 오디오 버퍼 요청 격리·재개 입력 순서

2026-09-29. SDL3·SDL2 패키지와 플랫폼 CI 검증을 완료했다.

## 변경

- SDL3 재생 장치와 마이크는 같은 전역 `SDL_HINT_AUDIO_DEVICE_SAMPLE_FRAMES`를 사용한다. 두 경로가 동시에 열리면 요청값이 바뀔 수 있었으므로 SetHint→Open→이전 값 복원을 하나의 잠금 범위로 묶었다. 출력 열기 실패의 오류 문자열은 힌트를 복원하기 전에 보존한다. 이 잠금은 장치를 열 때만 사용하며 오디오 콜백에는 추가하지 않는다.
- 오디오 설정에서 Audio sync를 직접 조절할 수 있다. 미리보기·취소·저장을 기존 설정과 연결하고 메뉴 상태도 갱신한다. 스레드 간 동기 플래그는 atomic으로 게시한다. 기본값과 저장된 선택은 바꾸지 않는다. 출력 설명은 요청 프레임과 실제 블록 크기를 함께 보여준다.
- 오디오 동기를 사용하는 도중 제어 요청이 대기를 중단했다면, 재개 시 남은 대기를 입력 샘플링 전에 끝낸다. 이미 샘플링한 입력이 대기 시간만큼 오래된 상태로 다음 프레임에 전달되는 일을 피한다. PCM 큐를 비우거나 입력을 두 번 처리하지 않는다.

## 장치 관측과 지연 한계

Windows 기본 출력에 무음만 전달하는 짧은 검사에서 SDL3의 WASAPI 드라이버와 별도 WASAPI shared 모두 요청 128·256·1024에 대해 48kHz/480프레임 블록을 보고했다. 실제 콜백도 480프레임이었다. IAudioClient3의 공유 엔진 주기를 별도로 질의한 결과 기본·최소·최대·기본 단위가 모두 480이었다. 이 장치는 공유 모드에서 10ms로 고정돼 있으며 요청 숫자를 줄여도 더 작은 주기를 제공하지 않는다. 이 결과는 한 endpoint의 관측이며 모든 Windows 장치의 제한이 아니다.

출력 블록 길이는 물리 스피커 지연이나 입력→화면 지연이 아니다. 코어 대기열·운영체제·장치·렌더링 지연은 별도로 남는다. Audio sync를 끄면 오디오 대기가 에뮬레이션을 지연시키지 않지만 두 시계의 속도 차이로 큐가 부족하거나 넘칠 수 있다. 이것만으로 실제 틱 노이즈 원인을 확정하지 않는다. 자동 클록 보정·독점 출력은 추가하지 않았으며 Sinc PCM·필터 계수·버퍼 용량·볼륨은 유지한다. 재개 입력 변경은 Audio sync가 꺼진 경로에는 효과가 없다.

## 검증

- 같은 SDL3 힌트 복원/실패 보존 검사는 1.1.211 소스에서 실패하고 수정 소스에서 통과했다. 힌트가 없던 경우와 기존 값이 있던 경우, 성공·실패 후 복원, 원래 오류 보존을 확인한다.
- 로컬 집중 검사 6개: 동기 미리보기/취소·저장, 보조 인스턴스 설정 제한, SDL3 힌트 열기, 기존 오디오 콜백, 키보드 입력 검사가 통과했다. 버퍼 콜백은 dummy 장치, UI는 offscreen으로 실행했다.
- 실제 장치 무음 검사에서 Stop 동안 source 콜백이 멈추고 Resume 뒤 다시 증가하며 Close가 성공했다. 이는 1.1.211의 기존 주기/수명 동작 근거이며 새 힌트 격리가 해당 장치의 주기를 줄였다는 뜻이 아니다.
- 전체 회귀는 CI에서만 수행한다. Windows x64·ARM64, Ubuntu, macOS, BSD, Core regressions CI가 모두 통과했다. 게임 플레이·장기 청취·물리 왕복 지연은 검증하지 않았다. 틱 노이즈 완전 해결이나 FPS/입력 지연 개선률을 선언하지 않는다.
