# 1.1.36 — ARM7 JIT 영역 판별과 LAN 수신 관찰

기준은 1.1.35(`279e7bf25d4731ad9a02b8dea1c0674ac0bcbafa`), 검증일은 2026-09-12다. CJ-02/06의 ARM7 LR-only 타이밍 차이와 NP-02/03·FS-17의 관찰 전용 계측을 독립 블록으로 구현했다. 아래 책임 버전의 Vulkan이나 전체 계획 완료를 뜻하지 않는다.

## ARM7 JIT의 잘못된 메모리 영역 판별

`ARMv4::DataWrite32`는 `DataRegion`에 정렬된 전체 guest 주소를 기록하고 JIT tracing이 그대로 복사한다. x64의 `Comp_AddCycles_CD`는 이를 4비트만 이동해 main RAM의 영역 번호 `0x02`와 비교했다. 예를 들어 `0x0201203C >> 4`는 `0x00201203`이므로 정상 main RAM을 다른 영역으로 분류했다. 이동을24비트로 고쳐 기존 메모리 비용 식이 올바른 영역을 선택하도록 했다. A64의 해당 판별은 이미24비트이며 ARM9 분기·interpreter·기존 비용 식은 유지했다.

생성 Thumb `PUSH {LR}`를 실제 RAM과 native x64 dispatch로 실행했다. 다섯 코드/스택 timing profile을 두 halfword 정렬에서 확인하며 최초 tracing과 캐시된 native 실행을 구분한다.

| 코드 / 스택 | 기존 모델 입력 | interpreter | cached x64 수정 전 → 후 |
|---|---|---:|---:|
| main RAM / main RAM | 기본 C=8, D=9 | 17 | 14 → 17 |
| main RAM / main RAM | 인위적 C=4, D=9 | 13 | 10 → 13 |
| main RAM / main RAM | 코드 N=4/S=1, D=9 | 13 | 10 → 13 |
| main RAM / private WRAM | C=8, D=1 | 8 | 8 → 8 |
| private WRAM / main RAM | C=1, D=9 | 9 | 10 → 9 |

JIT와 fastmem은 각각12/20에서20/20으로 통과했다. 각20건은 최초 tracing10건과 실제 cached native10건이다. 제품 코드가 바뀌지 않은 interpreter의10/10 대조를 재사용했고, 기존 LR/PC 스택 상태는 JIT·fastmem 각각24/24로 유지됐다. 생성 명령 바이트에서도 사이클 더하기가 C4/main/main의10→13, 기본14→17, private-code/main-data의10→9로 바뀌었다. 일괄적인 사이클 가산이 아니다.

이 수치는 기존 melonDS의 timing 모델에 대한 검증이다. DS 실리콘의 절대 wait state·버스 경합·overlap이 정확하다는 증거가 아니다. [1.1.35의 빈 Thumb 명령 관측](1.1.35.md)은 그대로 보존하며 빈 PUSH/POP의 미확정 동작을 새 정답으로 채우지 않는다. native A64·실기·비정렬 메모리 후속은 남긴다.

## LAN 통계를 설정 변경 없이 표시

기존 LAN 로비의 참가자 목록 아래에 수신·대기·응답 통계를 표시한다. 기존1초 갱신에서 한 번 snapshot을 읽는다. 새 타이머·설정·자동조절이나 통신 형식 변경은 없다.

- 수신은 검증 후 큐에 들어온 MP 프레임 수이며, 현재/최대 큐 길이·기존16ms 만료·잘못된 MP 프레임·서비스 오류를 구분한다. 만료/거부를 네트워크 손실률로 표시하지 않는다.
- 양수 대기를 요청한 ENet 서비스 호출의 실제 host 경과 시간으로 평균·최대·표본 수를 표시한다. peer ping이 아니며 OS 스케줄링 정지도 포함한다.0ms 관측과 표본 없음을 구분하고, 시계 역행은 별도 횟수로 기록해 평균에서 제외한다. 즉시 확인에는 추가 시계 읽기가 없다.
- 응답 수집마다 각 sender의 첫 기여, 중복 응답, 일부 응답만 반환한 횟수와 작업 상한 반환을 구분한다. 상한 횟수는 기존64개 이벤트 처리와64개 MP 수집 경계의 합이며 버린 패킷 수가 아니다.

16개 u64로 세션당128바이트를 사용한다. 기존 세션 잠금 아래 갱신/읽기하며 packet별 history·log·할당을 추가하지 않았다. 연결 종료 뒤 합계는 남기고 큐 길이는0이 된다. 다음 연결 준비 때 초기화한다. 관찰은 수신 데이터를 소비하거나 설정을 바꾸지 않는다. [1.1.35의 느린 참가자 유지와 대기 정책](1.1.35.md)을 보존한다.

기존 실제 LAN 구현 fixture는 계측 전43/47, 계측 후47/47이다. 유효/만료/잘못된 프레임, 요청71ms 대비 실제40ms, 새 sender·중복·부분 반환 뒤 남은 packet, 서비스 오류·시계 역행·작업 상한·재연결 초기화를 검증했다. 실제 ENet loopback도 통과했다. 별도 UI 검증에서는 생성40바이트 command의 정확한 payload/timestamp와 실제 세션 통계의 화면 표시, 연결·취소·DNS·재시도·host 종료를 한 번 실행해 통과했다. offscreen522×391 로비의 통계 세 줄을 확인했다. 실제 사용자 설정·게임·다른 DPI의 검증은 아니다.

## 관찰 비용

동일한 생성 전달 fixture와 실제 ENet packet 할당/해제, Qt QElapsedTimer, GCC -O3를 사용해 변경 전후를 대조했다. 버전/경로마다9회, 실행마다2,000 packet 준비 후200,000 packet을 측정하고 CPU 하나에 고정했다. 실행 순서는 섞었으며 빌드/다른 소유 테스트를 겹치지 않았다.

| 경로 | 기준 중앙값 (최소~최대), ns/packet | 현재 중앙값 (최소~최대), ns/packet |
|---|---|---|
| 즉시 확인 | 385.293 (373.171~395.918) | 383.418 (373.296~389.434) |
| 양수 대기 요청 | 395.637 (380.354~413.531) | 453.853 (437.324~468.276) |

즉시 확인의 범위는 겹치므로 속도 향상으로 판정하지 않는다. 양수 대기 경로의 중앙값 차이는 약58ns다. 실제 소켓은 사용하지 않았고 서비스가 준비된 프레임을 즉시 반환하는 CPU 비용 대조다. 실사용 대기시간·LAN 처리량·게임 FPS·UI 갱신 비용이나 p95/p99를 입증하지 않는다.

## 통합 검증과 남은 조건

최종 Windows Release 빌드와 **CTest637/637·실패0·건너뜀0**이 통과했다. 전체 CTest는 병렬도2로 한 번 실행했고80.55초였다. 실제 application object를 연결한 Qt 검증에서도 생성 guest의 상태·진행 보존, 설정 Cancel, shader/할당/표시 실패 뒤 복구와 명시적 재시도를 확인했다. 주입한 실패를 실제 장치 고장 재현으로 확대하지 않는다. 배포 EXE·소스 식별·패키지 결과는 배포 manifest에 별도로 기록한다.

일반 게임 저장·설정·LAN v1과 상태 writer14.2는 유지한다.14.2를 읽지 못하는 구버전이 새 상태 파일을 읽는 제한도 그대로다.1.1.35의 생성 프레임 구버전 대조는 과거 해당 소스의 결과이며 이번 버전에서 반복한 통신 수락으로 세지 않는다. 원본 클라이언트의 original/original 대조에서도 나타난 연결 실패는 미해결이다.

다음 통신 작업은 제한된 지터·손실·재정렬·느린 peer·절전·합류/이탈에서 관찰값과 실제 진행을 대조하는 것이다. 큐 나이 분포·빈 반환·UI 계측 비용과 관측 부족/악화 시 복귀 조건은 후속이다. 자동조절은 그 근거를 확보한 뒤 판정한다. 실제 두 PC·혼합 구버전 게임·DS/DSi 실기·장기 사용·다른 OS/native ARM64 및 별도 Android 프로젝트 수락은 계속 남는다.
