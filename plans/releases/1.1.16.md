# 1.1.16 — 목록 전송·PC 값·명령 상태 복원

상태: 구현·Windows 빌드·로컬 회귀 완료. 기준 1.1.15. CJ-06과 CJ-03의 증분이며 기존 책임 버전 1.1.16의 OpenGL 과제 완료를 뜻하지 않는다.

## 5페이즈

1. **근거·재현:** 빈 목록의 공식 ISA 분류와 CPU별 호환 동작을 구분한다. 실제 ARM9/ARM7 guest 명령으로 interpreter·일반 JIT·fastmem의 주소·전송·PC·상태를 대조한다.
2. **수정:** ARM7 PC 한 word 전송과 0x40 writeback, ARM9 비전송·writeback을 분리한다. 일반 ARM7 STM PC 저장값과 이전 data cycle 재사용도 수정한다.
3. **통합:** 암묵 PC·상태 flags를 decoder에 반영하고 드문 빈 목록을 기존 JIT interpreter fallback으로 연결한다. 레지스터·CPSR·cycle 동기화와 ARM/Thumb 전환을 보존한다.
4. **검증:** 조건 결과가 바뀌는 두 번째 실행, 정상 목록, CPSR/은행 SP 복원, PC 숫자가 같은 상태 전환을 검사하고 전체 CTest·게임 전후 비교를 수행한다.
5. **배포:** Windows 실행 파일·소스·공개 계획을 버전으로 묶는다. 실제로 실행하지 않은 플랫폼·장치·명령 경계는 계속 남긴다.

## 원인과 변경

빈 ARM 목록은 주소 계산과 전송 루프를 모두 건너뛰어 writeback도 원래 값이었다. ARM7에서는 PC 한 word를 전송하되 주소·writeback 거리는 16개 레지스터에 해당하는 0x40으로 계산한다. ARM 상태 저장값은 명령 주소 A+12, Thumb STMIA는 A+6이다. LDM의 ARM/Thumb 유지와 `LDM {}^`의 SPSR 복원은 기존 CPU 메서드를 사용한다. ARM9는 전송 없이 베이스만 갱신한다. 이 CPU별 모델은 [GBATEK의 ARM 목록 설명](https://problemkaputt.de/gbatek.htm#armopcodesmemoryblockdatatransferldmstm)과 [Thumb 설명](https://problemkaputt.de/gbatek.htm#thumbopcodesmemorymultipleloadstorepushpopandldmstm)에 근거한다.

ARM7의 빈 STM IA/IB/DA/DB 주소·PC 값, 빈 LDMIA 및 Thumb 전송은 원저자의 [GBA ARM 테스트](https://github.com/jsmolka/gba-tests/blob/a7113b67e63f83a9b321696ddd7042ccfad6c881/arm/block_transfer.asm)와 [Thumb 테스트](https://github.com/jsmolka/gba-tests/blob/a7113b67e63f83a9b321696ddd7042ccfad6c881/thumb/memory.asm)를 대조했다. `LDM {}^`의 상태 복원은 [원 실기 보고](https://github.com/mgba-emu/mgba/issues/2127)가 있다. 이번 작업에서 그 보드 실험을 직접 수행한 것은 아니다. 감소형 빈 LDM과 W=0 등은 같은 주소·writeback 모델을 적용하며 별도의 실기 검증으로 주장하지 않는다.

일반 ARM7 `STM {PC}`도 가시 PC인 A+8을 그대로 저장했다. [ARM DDI0151C §2.2 표 2-1](https://ww1.microchip.com/downloads/en/DeviceDoc/ARM_920T_TRM.pdf#page=29)의 ARM7TDMI 행과 위 원 ARM 테스트 t510이 지지하는 A+12로 수정했다. interpreter와 두 JIT의 STM PC 소스에만 적용한다. 일반 PC 읽기·ARM9 저장값·비정상 Rn=PC 조합을 이 근거로 변경하지 않는다.

ARM9 빈 명령은 데이터 접근이 없는데도 이전 `DataCycles`를 더했다. 같은 명령의 비용이 이전 D=1/99에 따라 4/99로 달라지는 반례를 확인했다. 데이터 접근 없이 코드 비용만 더하는 명시적 호환 정책으로 바꿨다. 이 수치는 emulator 모델의 독립성 검사이며 ARM946의 빈 명령에 대한 실측 사이클 수가 아니다.

JIT는 빈 ARM7 LDM의 암묵 PC 목적지를 알아야 블록을 끝낼 수 있다. decoder의 source/destination·NZCV 의존성·복원 정보를 보완하고 x64/A64에서 기존 interpreter 호출 경로로 분기한다. 정상 목록은 기존 생성 코드를 사용한다. ARM9 비전송을 메모리 명령으로 집계하지 않아 이전 DataRegion도 전송 정보로 재사용하지 않는다.

추가로 ARM에서 Thumb로 복원하면서 숫자로 된 pipeline R15가 같아지는 경우, JIT trace가 이를 조건 불성립으로 오인해 다음 Thumb 명령을 ARM으로 해석했다. 실제 재현에서 undefined instruction 예외가 발생했다. branch-follow는 현재 명령 상태와 복원 후 상태가 같을 때만 허용한다.

## 검증과 남는 범위

수정 전 목록 전송 검사는 backend당 296회 중 124회가 실패했다. PC 숫자가 같은 상태 전환을 추가했을 때는 interpreter가 통과하고 두 JIT가 각각 한 번 실패했다. 수정 후 최종 **298회/각 backend**가 통과한다. 실제 코드·scheduler·두 번째 block 진입, IA/IB/DA/DB·W=0/1·조건 변화·정상 목록·메모리 sentinel·PC·NZCV·banked SP를 검사한다. ARM9 별도 관찰 CPU는 data bus 읽기/쓰기 호출 0과 이전 D 비용 독립성을 확인한다.

최종 Windows x64 프런트엔드 빌드와 전체 CTest **381/381, skip 0, 병렬8에서 9.19초**를 확인했다. UCRT64 GCC 16.2.0·Qt 6.11.2·SDL 2.32.10, C23/C++26·Release·JIT·OpenGL/Compute 구성이다. A64 코드의 통합은 소스 수준이며 이번에 빌드·실행하지 않았다.

두 DS 게임에 같은 생성 입력·software renderer를 사용해 각 3600프레임씩 현재 interpreter/JIT/fastmem과 이전 1.1.15 interpreter/JIT를 비교했다. 총 10회가 종료 0·실행 상태 유지였고, 두 게임 모두 현재 JIT=fastmem=이전 JIT, 현재 interpreter=이전 interpreter였다. 최종 프레임은 이전 도입부 화면과 같으며 interpreter/JIT 사이의 기존 차이는 남는다. 전체 상태 동등성·장기 플레이·호스트 속도 개선·입력 지연 수락으로 확대하지 않는다.

[ARM ISA DDI0100I](https://prog5.gricad-pages.univ-grenoble-alpes.fr/Projet/doc/ARM_v5.pdf#page=186)는 빈 목록을 UNPREDICTABLE로 분류하므로 이 구현을 모든 ARM 코어의 보편적 정의로 확장하지 않는다. 빈 Thumb PUSH/POP(B400/BC00)의 직접 원 실기 oracle은 제한한 원 테스트 조회에서 확보하지 못해 기존 동작을 유지한다. LR/PC 단독 B500/BD00은 빈 목록이 아니다. ARM9 직접 실측, 비정상 base/은행 레지스터 조합, 정확한 버스 사이클, native A64 및 앞선 실제 장치·장기 게임 수락은 남긴다.
