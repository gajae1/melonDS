# 1.1.06 — 파일 준비 실패와 저장 가져오기 보호

상태: 구현·Windows 빌드·로컬 회귀 검증 완료(2026-09-10). 기준 소스: 1.1.05. 이번 증분은 FS-02의 ROM·save import 읽기, FS-07 archive 처리, FS-14의 RTC 파일 경계를 다룬다. 책임 버전과 배포 순서는 구분한다.

## 이번 증분의 5페이즈

1. **반례:** 큰 길이의 축소·부분 읽기·할당 실패, 누락된 archive 멤버·손상 데이터, 읽기 전 import reset, 잘린 RTC와 쓰기 실패를 정상 입력과 대조한다.
2. **입력 준비:** 원래 표현 가능한 길이를 검사하고 모든 읽기·디코딩을 완료한 뒤 바이트와 경로를 함께 적용한다. 자원은 실패 경로에서도 해제한다.
3. **적용과 보존:** import의 준비→reset→SRAM 적용을 한 메시지에서 처리하고, RTC는 임시 파일의 전체 쓰기·commit 성공으로 교체한다. 도달하지 않는 firmware 재읽기 API를 제거한다.
4. **검증:** 생성한 ZIP/7z/tar, 실제 Qt 임시 파일·코어 RTC·카트 SRAM, 메시지 dispatcher를 사용한다. 전체 Windows 빌드·회귀와 배포 의존성을 확인한다.
5. **배포:** 동일 커밋의 소스·계획·실행 파일을 묶고 포크 master에 반영한다. 게임·장치 수락과 더 넓은 저장 정책의 미확인 범위는 따로 기록한다.

## 변경 범위와 계약

| ID | 이번 변경 | 남은 범위 |
|---|---|---|
| FS-02 | raw ROM 길이·전체 읽기·할당 실패, 출력 준비 후 적용, import 파일을 reset 전에 검증 | 다른 BIOS/firmware·부가 파일의 읽기 경계, 모든 reset/할당 부작용 |
| FS-07 | archive header EOF/오류·멤버 확인, 자원 해제, 크기·이름·전체 읽기와 출력 보존 | 모든 archive 형식·암호화·실제 최대용량·느린 매체/취소 |
| FS-14 | RTC 전체 입력 검증과 원자적 저장 | 다중 프로세스·독립 RTC 파일 정책·날짜/시간 및 게임 수락 |
| FS-02/05 | 불필요한 firmware 재읽기와 SaveManager reload API 제거, 기존 경로 이동 유지 | host save manager 할당 실패·장기 worker 경쟁 |

ROM의 바깥쪽 크기 제한은 기존 raw/Zstd 경로의 1 GiB를 유지한다. 각 카트 parser가 지원하는 실제 형식과 크기는 별도다. 파일명 확장자에 따라 더 작은 새 한도를 부여하지 않는다. 실패하면 caller가 가지고 있던 출력 바이트·길이·이름은 그대로 남는다. 상대 경로의 archive도 부모 경로가 빈 문자열로 계산된다.

전체 읽기로 채울 ROM·archive·import 임시 버퍼에는 표준 `make_unique_for_overwrite`를 사용한다. 초기화되지 않은 바이트는 읽기 성공 전에 적용하지 않는다. 별도의 성능 향상 수치는 주장하지 않는다.

저장 가져오기는 삽입된 카트가 있을 때 입력의 0/과대 길이·읽기 실패·할당 실패를 먼저 처리한다. 성공한 입력만 reset하고, SRAM 적용이 끝난 뒤 오디오 callback과 실행을 재개한다. 실패한 입력은 실행/일시 정지 상태와 pause 깊이를 바꾸지 않는다. 아직 reset 때 활성화될 대기 카트도 허용한다.

카트 SRAM보다 짧은 저장을 가져오면 기존처럼 앞부분만 갱신한다. 저장 callback에는 전체 SRAM 크기와 갱신 범위를 전달해 나머지 바이트가 파일에서 잘리지 않게 한다. `.dsv` 등 기존 입력의 뒷부분 처리와 카트별 저장 형식을 재정의하지 않는다.

RTC는 기존 `rtc.bin` 이름과 바이너리 구조를 유지한다. 현재 정책은 인스턴스들이 같은 파일을 사용하며 마지막으로 성공한 저장이 남는 방식이다. 이번 원자적 쓰기는 파일 손상 방지이며 독립 인스턴스별 RTC 정책 변경이 아니다. 읽기 실패는 현재 RTC 상태를 유지하며 쓰기 실패는 로그에 남긴다.

SaveManager 재읽기는 reset이 새 관리자를 만들고 이미 같은 경로인지 비교한 뒤 호출하는 유일한 production 분기였다. 도달 가능한 소비자가 없어 해당 분기와 reload API를 제거했다. 같은 게임의 경로 이동은 기존 lock·primary/secondary·pending을 유지한다.

## 검증 기록

수정 전 ROM의 길이 축소·할당 종료·출력 변경과 RTC 부분 적용·직접 쓰기 실패를 확인했다. archive의 정상 ZIP/7z/tar 목록·추출 대조는 통과했고 누락·잘린 데이터·청크 읽기·메타데이터·자원 오류 반례가 실패했다. import는 정상 적용 중 callback 활성화와 잘못된 입력의 선행 reset을 재현했다. 실제 카트의 짧은 import에서는 메모리의 뒷부분이 남아도 저장 파일이 짧아지는 반례를 확인했다.

Windows 전체 빌드가 성공했고 CTest 158/158, skip 0, 22.97초를 확인했다. 여기에는 FrontendFileIO 22개, ArchiveIO 15개, import 메시지 10개, 기존 상태 복원과 실제 OpenGL/Compute 출력 비교가 포함된다. 짧은 저장 가져오기는 실제 카트→SaveManager 경로에서 파일의 전체 길이와 뒷부분 보존을 대조했다.

빌드는 UCRT64 GCC 16.2.0, CMake 4.4.3, Qt 6.11.2, SDL 2.32.10, libarchive 3.8.9, Zstd 1.5.7의 Windows x64 구성이다. C23/C++26, JIT/OpenGL과 선택적 AVX2/AVX-512 경로를 유지하며 LTO는 끈 구성이다. 지원 명령어 경로를 모든 호스트에서 실제 실행했다는 뜻은 아니다.

배포 실행 파일은 개발 도구를 제외한 PATH에서 `--help` 종료 0을 확인했고, EXE/DLL 129개의 import 검사에서 누락 의존성이 없었다. 공개 계획 15개 문서의 상대 링크와 개인 경로 제외 검사도 통과했다.

## 검증 한계와 근거

FrontendFileIO는 실제 Qt 파일·zstd/libarchive·코어 RTC에 생성 입력을 공급하며 일부 read/size/allocator/write/commit 실패는 주입한다. StateLoadMessages는 실제 dispatcher와 public wrapper를 동기 전송 대역으로 연결해 순서를 확인한다. CartReplacement는 실제 카트 SRAM의 저장 callback을 실제 SaveManager에 연결한다. 전체 UI·실제 오디오 장치·게임 장기 실행을 한 번에 검증한 것은 아니다.

ZIP의 UTF-8 표시가 있는 한글 이름을 C locale에서도 대조한다. 인코딩 표시가 없는 기존 ZIP은 libarchive의 기존 해석을 유지하며 UTF-8로 추측 변환하지 않는다. 모든 인코딩 미표기 이름의 locale 독립성을 보장하지 않는다.

archive 처리의 반환값과 EOF 구분은 libarchive의 공식 [header 계약](https://raw.githubusercontent.com/libarchive/libarchive/master/libarchive/archive_read_header.3), [data 읽기 계약](https://raw.githubusercontent.com/libarchive/libarchive/master/libarchive/archive_read_data.3), [entry 크기 계약](https://raw.githubusercontent.com/libarchive/libarchive/master/libarchive/archive_entry_stat.3)을 기준으로 한다. 실제 설치 라이브러리와 생성 입력의 실행 결과를 별도로 확인한다.
