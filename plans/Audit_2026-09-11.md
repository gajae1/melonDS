# 2026-09-11 코드·계획·upstream 점검

기준은 1.1.28의 `04742e167eeba2b26b6099d9982a23c5931fba63`이다. 1.1.29의 변경 파일은 별도 구현·검증 기록을 따른다. 이번 점검은 전체 파일을 배정한 **1차 부분 감사**이며, 미열람 코드를 검토 완료로 세지 않는다.

## 원래 목표와 실제 개발

42개 책임 버전·125개 과제는 제품의 최종 목표다. 실제 1.1.29 출시는 LAN·입력·타이틀의 제한된 수정이며, 원래 책임 버전 1.1.29의 AES 전체 완료를 뜻하지 않는다. 반례를 해결한 구현과 Windows 검증은 축적됐지만, Vulkan·SDL3·PGO 및 native A64/Apple/Linux/BSD·실기·장기 게임 수락은 남아 있다. [전체 계획](Release_Plan.md), [실제 진행](Execution_Order.md), [검증 경계](Validation.md)

## 공식 upstream과 소프트웨어 호환

조회한 공식 안정 릴리스는 [1.1](https://github.com/melonDS-emu/melonDS/releases/tag/1.1)이고 master snapshot은 [906e9ebb](https://github.com/melonDS-emu/melonDS/commit/906e9ebb27da8c6a715cd7abab4abfe8a8d29427)이다. 우리 포크의 1.1.30 번호를 공식 릴리스 진행도와 비교하지 않는다.

MakeEmbed 경로, Android fastmem 선언 guard, VCOUNT hang 수정은 해당 포크 소스에 이미 있다. 카트/DMA·DSi Wi-Fi 등 다른 변경은 일부 함수와 패치 흔적만 대조했으며 최신 upstream 전체와 동등하다는 결과는 아니다. 특정 게임이 수정됐다는 과거 이슈 종료만으로 현재 실행 성공을 주장하지 않는다.

추가 재현 후보는 [WordleDS JIT 부팅](https://github.com/melonDS-emu/melonDS/issues/2622), [Metroid Prime Hunters 등의 고배율 Compute 오류](https://github.com/melonDS-emu/melonDS/issues/2683), [Zubo 로딩](https://github.com/melonDS-emu/melonDS/issues/2703), [DSi 장기 실행 저하](https://github.com/melonDS-emu/melonDS/issues/2658)다. 원문 보고와 포크의 재현을 구분한다. Compute 예산 초과 시 일부 tile을 버리는 제안은 출력 손실이 있으므로 정확성을 보존하는 최적화로 자동 채택하지 않는다.

## Android·macOS·Linux 계약

Android는 별도 앱과 코어 포크를 사용한다. 조회한 앱 `3f3a1c82`(2026-08-30)는 [코어 431ab4bd](https://github.com/rafaelvcaetano/melonDS-android-lib/tree/431ab4bd0003c4356e25fce89640ae1004579b9b)를 가리킨다. 그 코어는 C11/C++17, 앱은 CMake 3.22.1·C++17 설정인 반면 우리 루트는 CMake 3.30 이상·C23/C++26을 요구한다. 현재 앱은 자체 JNI·PlatformAndroid·Oboe·GLES 연결층에서 `core`와 `net-utils`를 연결한다. 따라서 그대로 코어 폴더를 교체하는 호환성은 제공하지 않는다. [앱 build 설정](https://github.com/rafaelvcaetano/melonDS-android/blob/3f3a1c8260850ce5f5ffe2b25ee4274b8674fa5f/app/build.gradle.kts), [native 연결](https://github.com/rafaelvcaetano/melonDS-android/blob/3f3a1c8260850ce5f5ffe2b25ee4274b8674fa5f/app/CMakeLists.txt)

이식 블록은 실제 NDK의 compiler/STL 기능, JNI·Platform API, 파일 URI·저장 정책, EGL/GL 헤더, 오디오·입력 lifecycle, A64 JIT/페이지/W^X·fault 처리 순서로 좁힌다. 현재 Windows Qt의 수정이 Android UI까지 적용됐다고 세지 않는다. Android 앱·장치 빌드는 이번 감사에서 실행하지 않았다.

직접 확인한 저장 상태 형식도 다르다. Android가 고정한 코어는 **13.0**, 우리 포크는 **14.2**이며 두 로더는 서로 다른 major를 거부한다. 이 조합의 savestate를 그대로 주고받을 수 없다. 일반 게임 저장은 별도 형식이므로 게임·저장 크기·경로를 확인하는 별도 이관 대상이다. [고정 코어의 상태 형식](https://github.com/rafaelvcaetano/melonDS-android-lib/blob/431ab4bd0003c4356e25fce89640ae1004579b9b/src/Savestate.h)

현재 Android의 MP 호출은 `MPInterface::Get()` 참조를 사용한다. 우리 포크는 이 API를 유지하지만 세션 교체와 겹치는 호출은 `Acquire()`로 호출 동안 소유권을 유지해야 한다. 성공 load 뒤 host 오디오 이력을 비우는 1.1.30 동작도 각 프런트엔드의 실제 load/rewind·callback 정지 경계에 연결해야 한다. 코어 파일 복사만으로 Android 쪽 연결을 완료했다고 보지 않는다. [현재 Android MP 호출](https://github.com/rafaelvcaetano/melonDS-android/blob/3f3a1c8260850ce5f5ffe2b25ee4274b8674fa5f/app/src/main/cpp/PlatformAndroid.cpp)

macOS/OpenBSD에서는 현재 fastmem을 명시적으로 끄는 분기가 있고 Apple x64의 native JIT도 빌드 조건으로 제한된다. Linux/Android에서는 페이지 크기와 mapping·signal 경로가 별도다. 이런 분기 존재는 해당 플랫폼의 실행 수락이 아니다. macOS의 context 수명·서명/실행 메모리, Linux의 X11/Wayland·오디오·입력·종료, ARM64의 생성 코드 실행은 native 환경에서 확인한다.

## 정확성과 최적화의 취급

정확성을 보존하는 최적화는 guest 값·flags·cycles·출력의 일치와 실제 workload 이득을 함께 요구한다. 고해상도·보간·필터·host underrun ramp처럼 출력을 바꾸는 선택은 실기 동등성과 따로 표시한다. AVX-512·BMI·ARM crypto·SVE/SME·Vulkan·PGO가 존재하거나 빌드된다는 이유로 속도 향상을 주장하지 않는다. 오디오 ramp는 잃은 PCM의 복구가 아니며, GPU 작업 생략을 알리지 않고 기본 동작에 넣지 않는다.
